# Successor Locks for Unmergeable Files

## Summary

This proposal adds causal exclusive locks for unmergeable files in Lore's free branching model. Each unmergeable file gains a server-side **chain latest** in each *lock scope*: a record of the file's content when the last editing session on it there concluded, and the revision that produced that content. An exclusive lock is granted only on a branch whose history of the file contains the chain latest's content — the branch is caught up, holding it at its latest revision, or ahead, having taken it in and edited further — so the branch already contains every concluded edit in its scope. Each unmergeable file becomes one linear edit chain per scope, embedded in the larger DAG; the lock acquisition is the gate that enforces successor-only progress within the scope, and the chain moves only when a lock holder concludes a session. Scopes are first-class server-side entities with their own identity and lifecycle, independent of any specific branch; each branch carries a `scope_id` in its metadata, inherited from its parent at creation. A repository has a default scope that all branches join unless they explicitly opt into another scope; a repository that only ever uses the default scope behaves identically to a global per-file chain (the degenerate case). The check is a single content comparison for a caught-up branch and a walk bounded by the chain latest's revision number otherwise, with no path-keyed state and no materialized (branch × file) indices.

## Motivation

Lore supports free branching: any user creates a branch, edits, and requests a merge. For files that merge by content (text, structured data), divergent edits across branches resolve at merge time. For unmergeable files — binary assets, opaque tool-managed formats — there is no such resolution: two divergent edits cannot be combined, so the only safe outcome is that one branch's edit becomes the new state and the other's work is discarded.

Lore's current exclusive-lock primitive prevents (through opt-in compliance) two concurrent edits to the same file by serializing access while the lock is held. It does not prevent the same file from being edited in parallel across branches over time. Locks are ephemeral: released explicitly once the edit is pushed, after which any branch can acquire a fresh lock on the same file. Nothing in a push releases a lock; `lore lock release` does (`lore-revision/src/lock/file/release.rs`), and so does the rollback a failed batch acquisition runs (`lore-revision/src/lock/file/acquire.rs`). Whether the lock is scoped globally or per-branch makes no difference — the contention is causal, not temporal. A user on branch B can hold an exclusive lock on file F, commit an edit, release the lock, and after this point in time a user on branch C — which has never observed B's edit — can acquire a new lock on F, edit it independently, and commit. The two edits then sit on two branches as competing versions of an unmergeable file. When B and C eventually merge, the conflict has no resolution path that does not silently lose work, even though the locks were correctly acquired and released.

The gap is not in exclusion. The current primitive correctly answers "is it safe to edit this file right now?" The gap is in causality: nothing answers "is it safe to take a new lock on this file from this branch — have all prior edits been made visible here?" Without that answer, exclusive locks alone cannot keep an unmergeable file's history coherent under free branching.

A second gap follows from the first. If every branch in a repository had to see every earlier edit to a file before editing it, lines of work that have no reason to wait on each other would block each other. Bug fixes to an unmergeable file on a long-lived release branch would force every editor on main to be downstream of the release-branch fix before they could lock the file — and vice versa. The same coupling makes free-form experimentation impossible: a designer trying out alternatives on a throwaway branch would freeze edits to the same assets across the rest of the repository until the experiment was merged or abandoned. The second gap is one of independence: lines of work that don't share edits, such as a release line and an experiment, must not block each other's editing of the same file.

This matters now because Lore targets workflows with large unmergeable working sets — game assets, design files, generated artifacts — where the cost of an unresolvable conflict at merge time is far higher than the cost of upfront serialization, and where parallel release lines and isolated experiments are standard practice. Lock-based protection of unmergeable files in Lore stays structurally incomplete at any scale until every edit starts from every earlier edit in its line of work, and independent lines of work edit the same file without waiting on each other.

## Goals / Non-Goals

### Goals

1. **Causal-safety check at lock acquisition.** Before granting an exclusive lock on file F on branch B, verify that B contains every concluded edit to F in its scope.
2. **Single linear edit chain per unmergeable file.** Concluded edits to an unmergeable file form one totally ordered chain within a scope, regardless of how the surrounding DAG branches.
3. **Bounded lock check at scale.** Tens of millions of files, tens of thousands of branches, high churn — lock check for a caught-up branch is one node read plus one lock-store operation, and otherwise a walk bounded by the file's own history, with no (branch × file) materialization and no global broadcast on push.
4. **Content-only chain advance.** Changing the *content* of an unmergeable file (its BLAKE3 hash on the tree leaf node) is an edit: it requires the lock, and the session's conclusion advances the chain. Metadata-only changes — mode, timestamps, extended attributes — and path-of-record changes (rename, move) never advance the chain, and merge through Lore's normal tree-merge mechanisms. They stay outside the lock protocol unless they change whether the file is unmergeable, as a rename can: a change that makes the file mergeable or unmergeable needs the lock like an edit.
5. **Identity by file_id, never by path.** All cross-branch state keys on the stable file_id (which survives moves) — path is input/output only.
6. **Actionable lock-denial errors.** A denied lock names the revision, branch, and scope of the current chain latest, so the user knows what to merge.
7. **Per-scope chains.** Independent lines of work — release branches, experimentation sandboxes — maintain independent chains for the same file. Edits in one scope never block lock acquisition in another. Scopes are separate entities with their own lifecycle; each branch carries a `scope_id` as metadata, set only at creation and defaulting to the parent's scope. A repository that only uses the default scope behaves identically to the global per-file chain model.
8. **Server-mediated enforcement.** Lock validation and lock release are integrated into the Lore server's push handler — not advisory client-side checks. The server is the only path that mutates chain latest and lock state, and it decides which files a push changes from the revisions' trees rather than from the client's account of the change, so clients cannot bypass the protocol by skipping the lock-acquire flow. This elevates the existing exclusive-lock primitive (which Motivation describes as relying on "opt-in compliance") to a first-class protocol-state mechanism.
9. **Policy-controlled strictness.** The strictness with which each primitive (lock state, chain latest) gates operations is a repository-policy choice (see Enforcement policy in Proposed Design). Under the default strict policy, the server refuses a push that changes an unmergeable file without holding its lock, and refuses a lock or a conclusion to a branch that's behind. Under advisory policy on either primitive, the server emits a warning and audit-logs in the same situations but accepts the operation. The server remains the authority either way — what changes is the response, not whether the server is in the loop.

### Non-Goals

- Specify how a repository defines, stores, and loads which files are unmergeable, or define a general file-attribute system. The server evaluates unmergeability on every push, so [Proposed Design](#unmergeability) states the cost that mechanism has to stay within, and leaves the mechanism itself to the implementation.
- Auto-merge prior edits on the requester's behalf when the lock check fails. The proposal requires the merge to have happened; tooling can suggest it.
- Enforce locks on mergeable files. Only the existing lock service locks a mergeable file; the new one refuses it. Such a lock is per-scope like any other lock, so it stops other branches in the scope from locking the file, but enforcement covers unmergeable files only and never refuses a push because of it.
- Tune lease operations beyond the minimum the lock contract in Proposed Design requires — renewal intervals, sweep cadence, zombie-cleanup policy. Those are operational choices.
- Make the in-memory `local` lock store durable. It loses its state on a server restart, with the consequences [Non-Functional Considerations](#non-functional-considerations) describes under Statelessness; persisting it to disk is later work.
- Limit how many locks one user holds. Scope-wide exclusive locks are a denial-of-service exposure by nature, and the design answers abuse with an administrator's bulk release and with revoking write access (see Security Considerations).
- Retire the existing lock service. Strict policy holds across client generations — an old client's unlocked push is refused, its lock request runs the caught-up check, and its release concludes only when its branch is caught up or ahead — so retiring that service is a maintenance question rather than a condition of the design.
- Define the complete message schemas of the new lock service and the scope RPCs: every message, field, and enum value. This proposal fixes what a compatibility review needs — the services and their streaming shapes, the transaction's server-assigned id, the key order the server verifies, and the fields existing messages gain — and the downstream spec carries the rest.
- Define transparent locks, acquired when a tool opens an unmergeable file for editing, and their coupling to file modification notifications. Integrating lock acquisition with file-edit notifications — so a lock is taken automatically when a user opens an unmergeable file for editing, and released on the push that concludes the work — is a follow-on design. The model proposed here supports such an integration directly (locks are server-side primitives that any client signal can trigger, the same signals already renew a held lock's lease, and push releases the lock as a first-class step), but the notification protocol, IDE and tool integration, and UX details live in a future LEP. `lore branch merge --auto-lock` isn't such a lock: it's an option the user types, and it proceeds with a merge, under the locks the merge needs, when the merge's pre-flight finds every one of them grantable.
- Merge or split scopes. No scope-level verb does either, now or later. Both are already expressible through branches: folding scope A into B is merging A's branches into B's, each an edit in B, then archiving A, and splitting is creating a scope and branches in it. A scope-level merge would have to reconcile two independent chain latests of one file with no common chain, which is the unresolvable conflict this proposal exists to prevent.

## Proposed Design

Lore tracks two separate primitives, not just locks.

┌────────────┬───────────────────────────────────────────────────────────────────────────┬──────────────────────────┐
│ Primitive  │                             What it surfaces                              │      Temporal role       │
├────────────┼───────────────────────────────────────────────────────────────────────────┼──────────────────────────┤
│ Lock       │ "F is being modified right now by branch B"                               │ Present-tense, in-flight │
├────────────┼───────────────────────────────────────────────────────────────────────────┼──────────────────────────┤
│ Causality  │ "F has been modified up through revision X; your branch's view is at < X" │ Past-tense, settled      │
└────────────┴───────────────────────────────────────────────────────────────────────────┴──────────────────────────┘

- Locks address synchronization — coordination of ongoing work. A lock surface answers "is anyone editing F right now?" — which is useful for coordination, UI displays, and "ping the lock holder" flows.
- Causality addresses versioning — coordination of historical state. The change-tracking chain answers "is my version current?" — which is useful for status displays, pre-flight checks, "do I need to merge before I start?"

Two coupled mechanisms realize these primitives: a **scope system** that divides causality among independent lines of work, and a **change-tracking chain** that records the per-(scope, file) sequence of concluded edits. The sections below detail each, and the lock-acquisition check joins them.

The **scope system** divides lock causality into independent regions. A scope is a first-class server-side entity with a stable id and its own lifecycle, independent of any branch. Every branch carries a `scope_id` in its metadata; at branch creation, the new branch inherits its parent's `scope_id` by default, or names a different scope explicitly, and nothing changes it afterward. Two branches in the same scope share lock causality for unmergeable files; two branches in different scopes do not. Every repository has a default scope whose identifier derives from the repository's own, so it exists without being created; a branch that names no scope is in it, so every branch lands in the default scope by inheritance unless it or an ancestor opts elsewhere. A repository that never creates other scopes operates as a single global causality region, the degenerate case.

The **change-tracking chain** is the causality primitive, the conceptual linear sequence of concluded edits to an unmergeable file within a scope. Each link is the revision that produced the content an editing session on the file concluded with; the chain is linear by construction because only a lock holder adds a link, and a lock is granted only to a branch that already contains the chain's most recent link. The chain itself is *not* materialized as a separate data structure — its links are ordinary revisions in the revision graph, indistinguishable from any other revision. What the server materializes is one record per `(scope_id, file_id)` pair concluded in the scope: the **chain latest**, naming the chain's most recent link and F's content there. This proposal always qualifies the term, because a branch's *latest* — the pointer to its most recent revision — is a different thing; the stored record is the *latest entry*. A branch is **caught up** on F in its scope when F's content at its latest revision equals the chain latest's content, and **ahead** when F's content history on the branch contains it further back — the history Lore's per-file-id back-pointer index already records, one link per revision that modified the file. Caught up is a single comparison; telling ahead from **behind** walks that history, bounded by the chain latest's revision number.

The chain moves only when a lock holder concludes a session, at a push or a release the server sees: the holder's push to the branch that holds the lock, which concludes by default unless the holder keeps the lock, and always for a file it deletes; a push that carries the holder's work into another branch and names the file to unlock; the holder's release that asks to conclude, for work that someone else's merge carried into another branch; and the release a client that predates this proposal already issues, which concludes at the holder branch's latest revision when that branch is caught up or ahead there, or, under chain-advisory, behind. Nothing else writes the chain. A push that changes the file without holding its lock never does — under strict policy the server refuses it, and under advisory policy it lands and the server records it as off-protocol — so nothing moves the chain under a held lock, and no two pushes race to write it. The chain is the protocol-level abstraction; the latest entry plus Lore's back-pointer index are everything required to enforce it.

**What the protocol protects is held sessions and concluded chain links.** While a session holds the lock, no other branch in the scope, and no other user on the holder branch, can edit the file; once a session concludes, every branch that wants to edit the file has to contain its result. An edit the holder published but didn't conclude is the holder's risk once the lock goes — by a release, a lease expiry, an administrator's force-release, or a restart of the in-memory lock store: another branch can then acquire, conclude, and overtake it. A push to the holder branch concludes by default, so an edit stays published but unconcluded only while its holder keeps the lock across pushes, or after a merge carried it into another branch without concluding. Nothing is lost silently. The server refuses a later attempt to land the unconcluded edit under strict policy, because its branch doesn't hold the lock or is behind, and records it as off-protocol under advisory policy. The lease renewal the lock contract describes, and the warning `lore lock release` gives, keep a session from ending this way by accident. Concluding by default has a cost of its own: the chain can advance to work on a feature branch before that work lands, a trade [Risks and Assumptions](#risks-and-assumptions) records.

The lock-acquisition check joins the two mechanisms: a lock is granted only if the requester is caught up or ahead on the (scope, file) chain for its own scope. Cross-scope interaction happens only at merge time, where a merge bringing unmergeable-file edits across scope boundaries is an edit in the target scope, under a lock held there (see Cross-scope merges below).

*Figure 1. Three scopes, each with its own independent chain latest for the same unmergeable file F. Branches inherit scope from their parent at creation; lock acquisition compares F's content at the branch's latest revision against the chain latest in the branch's own scope only, and walks F's history on the branch when they differ.*

```
┌─────────────────────────────┐  ┌─────────────────────────────┐  ┌─────────────────────────────┐
│  scope: main                │  │  scope: release/1.0         │  │  scope: experiment          │
│  ──────────────             │  │  ──────────────────         │  │  ──────────────             │
│   main ──► feat-A           │  │   release/1.0 ──► hot-fix   │  │   sandbox ──► expt-A        │
│        ╲                    │  │                             │  │                             │
│         ─► feat-B           │  │                             │  │                             │
│                             │  │                             │  │                             │
│   chain latest(F) = R8      │  │   chain latest(F) = R12     │  │   chain latest(F) = R3      │
└─────────────────────────────┘  └─────────────────────────────┘  └─────────────────────────────┘

  lock F on feat-A   →  caught-up-or-ahead check vs chain latest(F) = R8   in scope `main`
  lock F on hot-fix  →  caught-up-or-ahead check vs chain latest(F) = R12  in scope `release/1.0`
  lock F on expt-A   →  caught-up-or-ahead check vs chain latest(F) = R3   in scope `experiment`

  chains across scope boundaries are independent — an edit in any scope
  does not affect lockability of F in any other scope.
```

### Scopes (Goal 7)

A scope is a server-side entity identified by a stable `scope_id`, carrying a human-readable name and its own lifecycle (create, rename, archive, restore, purge) independent of any particular branch.

Branches are *members* of a scope via a `scope_id` field in branch metadata. A branch's scope is fixed at creation: a branch created from a parent inherits the parent's `scope_id` by default, or names a different `scope_id` explicitly. Stacked branches inherit transitively through their parent chain. The server assigns the scope when it creates the branch, from the scope the request names or else from the parent's, so inheritance holds for every client, including one that predates scopes. This proposal treats scope assignment as immutable after branch creation, and leaves reassigning an existing branch into another scope to a follow-on (see Unresolved Questions). Only branch creation writes a branch's scope, on the server: no branch-metadata write can add, change, or remove it. Adding one is the case that matters — a branch in the default scope records no scope, so a metadata write that could add one would move that branch, `main` included, into an empty scope with no chain.

Every repository has a **default scope**, whose identifier derives from the repository's own, so it exists without ever being created or stored. A branch with no recorded scope is in it, which is every branch that exists before this proposal ships. New branches whose parent is in the default scope join it. A repository that never creates additional scopes operates entirely within the default — functionally identical to a global per-file chain — and stores no scope state at all. The default scope's name, `default`, is reserved: `lore scope create default` is refused, so no created scope shadows it in name lookups. It takes no lifecycle verb: it's always named `default`, and it can't be renamed, archived, or purged, because every branch with no recorded scope resolves to it.

Scopes are typically created to isolate long-lived release lines (each release line is a scope, taking backports without blocking main) or to wall off experimentation (a sandbox scope where unmergeable-file edits do not propagate constraints to production work). Scope creation is independent of branch creation: a user creates a scope, then creates one or more branches assigned to it.

A third use case is the **short-lived isolation scope**, complementary to the default-scope degenerate case. The user creates a fresh scope, assigns a single branch to it, does work that should not interact with any existing lock chains — no causality check against any other scope's latest entries — and merges to a target scope when done. At merge time, cross-scope merge semantics apply: the merge is an edit in the target scope on the same terms as any edit there — a held lock on the target for each unmergeable file the merge changes — and resolving conflicts there. This is an explicit escape hatch for one-off work that has to happen without waiting for other in-flight locks or chains — urgent hotfixes, throwaway prototypes, parallel "what-if" iterations on the same asset — and accepts at-merge conflict resolution as the trade-off. A file changed on both sides is a merge conflict that the target-scope holder resolves, so isolation trades the lock wait for an explicit conflict at merge and loses nothing silently. The resolver can pick their own side and discard concluded edits, but a lock holder inside one scope can already overwrite a file with any content: the protocol protects against edits made unaware of each other, not against deliberate overwrites. Mechanically identical to other scopes; the difference is intent and lifecycle. So the design has two degenerate cases at opposite ends: a repository using only the default scope (one global chain, maximum coupling) and a repository spinning up a per-branch isolation scope (no shared chain at all, conflicts deferred to merge).

Lore stores scopes in its mutable store the same way it stores branches ([ADR 00002](../developing/decisions/00002-branch-tracking-in-mutable-store.md)), as two paired records mirroring a branch's id-to-metadata and name-to-id pair (the key types are listed under [Compatibility](#compatibility)). One maps `scope_id → scope metadata` (the scope's existence and metadata); the other maps `scope_name → scope_id` (the human-readable name, also serving as the "is this scope active?" lookup). The `scope_id` is the canonical identifier — what branches store in their metadata, what latest and lock entries key on. Names are purely a human-facing pointer to that id; renaming or detaching the name affects no state outside the scope's own records.

Archiving a scope (`lore scope archive`) is therefore a soft operation: removing the `scope_name → scope_id` mapping takes the scope out of discovery (it disappears from `lore scope list` and name lookups fail), but the `scope_id`, its metadata, its latest entries, and any branch metadata that references it all persist. Branches assigned to an archived scope continue to function — their lock checks still resolve against latest entries keyed by the still-valid `scope_id` — and a branch created off a parent in an archived scope still joins it. Reinstating the name mapping (`lore scope restore <scope-id> <name>`) brings the scope back into normal discovery. Archive is the everyday lifecycle action and is fully reversible. Purge (`lore scope purge`) is the permanent removal — clearing the metadata and every latest entry too — and requires that no live branch still names the scope. Archived branches don't block it: archiving a branch is how Lore deletes one (`delete_branch_detached`, in `lore-server/src/grpc/mod.rs`), and nothing removes a branch for good, so if archived branches blocked purge, no scope that a branch had ever joined could be purged. An archived branch can't reach the purged entries either: the server refuses to restore an archived branch that names a purged scope, with a message saying the scope is gone, and its work stays reachable by merging it by id (`lore branch merge --id`).

Creating a scope takes only write access to the repository, because an isolation scope nobody else uses harms nobody and should cost nothing to reach for. Renaming, archiving, and restoring one — changing a scope other people may depend on — take repository administration or the scope's creator, and purge, the one irreversible verb, takes repository administration alone.

### Per-file chain latest (Goal 1, Goal 2, Goal 7)

The server materializes one record per `(scope_id, file_id)` pair concluded in the scope — the **latest entry**, which holds the file's chain latest — holding the file's content when the chain's most recent session concluded, and the revision that produced that content:

```
key:    Hash(scope_id, file_id)   // collision-resistant derivation, distributes evenly across keyspace
value:  latest_revision           // revision hash that produced latest_content
        latest_content            // the file's content hash when the most recent session concluded; for a delete, the last concluded content
        deleted                   // set when that session concluded by deleting the file, to the revision that concluded the delete
```

Carrying the content alongside the revision is what keeps the caught-up check to a comparison; the revision is what the denial message and the audit trail name. The revision is the one that *produced* the content, not the one the session concluded on: the server follows the file's history back from the concluding revision past every revision that only carried the content — a merge that took the file unchanged from its other parent, a rename, a metadata change — to the one that authored it. That's what keeps the walk's bound sound, as [Why the content check is sound](#why-the-content-check-is-sound) shows, and it costs one lookup in the file's history plus one read per revision it steps past. The record carries no branch or timestamp for the chain latest — they're derivable from the revision and would only duplicate authoritative state, and UX surfaces resolve them lazily on the error path. The one exception is the **off-protocol marker**: when a published edit lands that the chain didn't approve, a behind conclusion under chain-advisory included, the entry records the most recent such edit's revision, branch, and time until the next conclusion that wasn't behind clears it, because that edit is exactly what the revision history alone wouldn't flag. The audit trail records every instance.

The entry count scales with the **(scope, file) pairs concluded in each scope or seeded there by backfill**, live and deleted alike: a concluded delete leaves a tombstone rather than removing the entry (see [Content-only chain-link semantics](#content-only-chain-link-semantics-goal-4)), and only a scope purge reclaims either kind. A live entry holds three 32-byte hashes — its key, the revision, and the content, 96 bytes — plus the two keys of the scope index that purge enumerates, which carry the 16-byte scope id with a shard suffix and the 16-byte file id: about 130 bytes. On a tombstone the deleted field names the revision that concluded the delete, another 32 bytes, for about 160. An off-protocol marker, while one is set, adds a 32-byte revision, a 16-byte branch id, and an 8-byte time, about 56 bytes more. That puts an entry at about 130 to 220 bytes, before the store's own per-item overhead, which these figures leave out. A retired scope of a million entries without markers, at 130 to 160 bytes each, holds about 150 MB until it's purged. The count also doesn't multiply across scopes the way "live files × scopes" suggests, because a scope accrues an entry only for a file concluded *in that scope* — a short-lived isolation scope touching five assets costs five entries whatever the repository holds.

**These entries live with the lock state rather than in the mutable store.** An earlier draft of this proposal put them in the mutable store, on the grounds that its native hash-to-hash shape fits. Two properties of the mutable store rule that out. Latest entries are never enumerated by key, so they need nothing the mutable store uniquely offers; and scope purge and capacity reporting both have to answer "every entry in this scope," which the mutable store can't: these keys would be a hash of `(scope_id, file_id)`, and it lists keys only by partition and key type, with no predicate (`MutableStore::list`, in `lore-storage/src/mutable_store.rs`). A store that can carry a scope index answers both, and the lock store already needs to be that store because an acquisition reads the latest entry and reserves the lock together. Scopes, which *are* enumerated, do live in the mutable store.

### Lock acquisition (Goal 1, Goal 3)

For `lock F` on branch B given path P:

1. Determine `scope_id = scope_of(B)`. Branch → scope is a branch metadata lookup. The caller needs the permission a push to B takes, and B becomes the holder branch (see the lock contract below).
2. Resolve F at the revision the request names, determining `file_id`, and read F's content at B's latest revision as the server holds it. (Resolution failure returns "no such file in your branch" before any lock state changes, so a file that isn't pushed yet, or a resource that isn't a file, can't be locked.) The caller addresses the file by node identity rather than by path, so no path crosses the wire in either direction; the server reconstructs a path when a person needs to read one.
3. Once `file_id` is known, reserve the lock: insert an entry into the lock state for `(scope_id, file_id)`, failing with contention denial if an entry already exists. Branch and user together decide contention: an entry B already holds counts as B's session, and grants, only for the user the entry records, or for one holding the permission to conclude on another user's behalf, a repository `Owner` or `Admin` (see [Enforcement policy](#enforcement-policy-goal-9)); an entry that the branch an acquisition moves its locks from holds for the caller moves to B, as [Moving a lock to another branch](#moving-a-lock-to-another-branch-goal-1) describes; any other caller is denied for contention, whatever the policy, as on any other branch. This is the actual mutex; holding it pins the chain latest for the validation that follows — only a lock holder writes the chain, so no concurrent writer can advance it.
4. After the reservation succeeds, load the latest entry for `(scope_id, file_id)`.
5. Compare, and grant on either of two relations. **Caught up** — F's content at B's latest revision equals the entry's content. **Ahead** — it doesn't, but F's content history on B contains it, established by a walk bounded by the entry's revision number. An absent entry is first-edit semantics — the file has never concluded in the scope, the scope was purged, or the repository's backfill hasn't completed — and also grants. A tombstone judges B against the file's last concluded content, as [Content-only chain-link semantics](#content-only-chain-link-semantics-goal-4) describes. Otherwise B is **behind**: drop the reservation (it never held anything) and deny with the chain latest's revision and the scope in the error payload. A walk that runs out of its hop budget before it can place B denies too, as **indeterminate** rather than behind; a repository `Owner` or `Admin` can grant past that result, never past a proven behind.

Granting to an ahead branch is what Goal 1 asks for — it "contains every concluded edit to F," which is the requirement, and caught-up is merely its zero-hop case. A branch gets ahead legitimately in several ways: through advisory policy, after its own lock went without concluding — by a release, a lease expiry, or a force-release — from a concluded session's intermediate revisions, or when backfill seeds a chain from content the branch already descends from. Denying those protects nothing and blocks work sitting ahead of the protocol rather than behind it. What ahead promises is containment, not that the branch's unconcluded work is safe: two branches can both be ahead with different unconcluded edits, and whichever concludes first leaves the other behind. That's the protection boundary stated at the top of this section — published but unconcluded edits are their holder's risk once the lock goes.

The ordering is deliberate: reserving the lock *before* reading the chain latest eliminates a race in which a concurrent lock-edit-commit-push cycle could complete between an early check and a later reservation, leaving the requester holding a lock against a stale chain latest. With this ordering, the chain latest observed in step 4 is stable for the rest of the operation because step 3 has already excluded every concurrent writer. Because the lock and the latest entry share one record, a single store operation can do both steps — reserve the lock and return the entry it found — so the ordering holds by construction rather than by sequencing two reads.

Cost: scope lookup (O(1) cached) + one node read to resolve F + one lock-store operation that both reserves the lock and returns the latest entry, since the two share a record. A branch that isn't caught up adds the bounded walk. The validation-fails path adds one lock-entry removal; on the busy-file contended path that removal is unavoidable work and matches the rate of contention.

The above describes the **strict-default behavior**. Under advisory chain-enforcement policy the step-5 chain-behind denial, and a walk that runs out of budget, become a warning and the lock is granted anyway; the audit trail records both the lock acquisition and the stale check the policy accepted. See Enforcement policy below.

### Multi-file acquisition (Goal 1, Goal 3)

Acquiring many locks at once is the common case — a folder rename, a multi-file change, a prefab whose dependencies span the tree — and Goal 1's check has to hold for all of them at once: a change that spans many unmergeable files is safe only if its branch contains every concluded edit to each of them. The acquisition has to be all-or-nothing where the caller needs it to be, and Goal 3's scale rules out a ceiling on how many files one acquisition takes.

The acquisition is a **stream, and the stream is the transaction**. The caller opens it against a branch and a revision, sends entries, receives an outcome for each as it's decided — revised before the confirm only when the stream yields to an older one — and ends with a confirm that holds every reservation or a close that cancels them. The revision resolves each entry to a file; the check reads the branch's latest revision once, when the stream opens, and judges every entry against it. Two properties follow, and both are the reason for the shape:

- **The server judges every entry against one view of the branch.** A server judges a request split into fixed-size batches against as many reads of the branch's latest revision as it has batches; one stream reads it once. No batching scheme recovers that, because the size limit is what forces the splitting.
- **There is no size limit to communicate.** The caller confirms or cancels the transaction as a whole — by confirming or by closing the stream — rather than listing what it was granted, and the server keeps that list itself. Nothing in the protocol bounds a transaction's width; what bounds resource use is how many acquisitions run at once.

Atomicity becomes the caller's policy rather than a protocol mode: it decides what to do with the outcomes before confirming, which expresses more than a fixed atomic-or-best-effort choice could — take a folder, but drop the meshes if the rig is contended. The outcomes don't arrive in entry order: the server answers a caught-up entry as it arrives, but holds back the entries whose check walks history and walks them in groups of up to 1,024, in the order the history is stored, so that entries sharing stored history share its reads. A caller that waits for every outcome before deciding therefore says when it has sent its last entry, which walks whatever the server holds; a caller that confirms without reading them can skip that, since confirming walks it too.

Two costs come with it, and neither is hidden. The client must present entries in a consistent key order, which the server verifies: overlapping transactions converge either way, because the oldest transaction always wins a conflict, but ordered entries meet at their first shared key, so the transaction that yields holds nothing in the overlap and throws away less. Racing eight transactions for the same forty files on a real DynamoDB table (`contrib/lock-model/scale.py`), every transaction completed in both orders, and the worst case across four runs was 200 to 228 attempts for one transaction in ascending order against 329 to 372 in random order. With sixteen transactions, ascending order still completed every one, in at most 482 attempts, while in random order one transaction reached the harness's cap of 1,000 attempts and gave up. Under a single batch the server could have sorted the entries itself. And a large acquisition becomes one indivisible unit spanning whatever timeouts and restarts occur in its window, where a split request degraded gracefully.

The server, not the client, assigns each transaction its id, time-ordered, in its first response. With client-chosen ids, a client that always sends the lowest id never yields, and two streams can share one; a server-assigned id means the oldest transaction wins every conflict and none starves.

### Moving a lock to another branch (Goal 1)

Work sometimes changes branch while its locks are held. `lore branch create` and `lore branch switch` both carry uncommitted edits to the branch they move to (`switch` discards them only with `--reset`), and a tool that moves a set of changes between branches does the same. The locks stay with the branch that took them, so a push of the moved work is refused for contention: the new branch doesn't hold the lock and doesn't carry the holder branch's work. Releasing on the old branch and acquiring on the new one leaves a gap in which another branch in the scope can take the lock, and for a set of files the gap spans the whole set.

So an acquisition can name the branch its locks come from. The acquisition on branch B judges each file as any acquisition does — caught up or ahead on the chain, with advisory policy and the indeterminate override applying as they always do — and each lock the source branch A holds for the caller moves to B when the acquisition confirms. The move is one conditional write per file, and it takes effect only while A still holds the lock in the same session. The lock is never free: an acquisition that closes without confirming, or a server that fails before it confirms, leaves every lock with A, and a session A concludes in the meantime stays concluded, with the file reported as not moved. A file A doesn't hold for the caller is acquired as usual, and a file another branch or another user holds is contention, so naming a source branch skips no check an acquisition makes.

A move doesn't conclude. The chain latest stays where it is, and the lock keeps the user it records and the chain latest it was granted against, while its lease starts afresh. Only the user the lock records can move it, as only the holder can release it, and the caller needs the permission a push to B takes, as any acquisition does. A and B have to be in the same scope, because a lock's key is its scope and its file; across scopes, a caller acquires in the new scope and releases in the old. Edits A published under the lock stay on A, unconcluded, as after a release. The acquisition reports each moved file whose content at A's latest revision matches neither the chain latest nor B, so the client warns about the edits it leaves behind, as `lore lock release` warns.

The CLI moves locks only when asked, with `lore lock acquire --from <branch>`. `lore branch create` and `lore branch switch` name the locked files whose edits they carry and point at that command, and move no lock themselves: a move decides what the source branch can push next, and a branch created for unrelated work while edits sit in the working tree would otherwise take that branch's locks with it.

### Why the content check is sound

The chain invariant — only the lock holder can produce the next chain link, and the lock holder must already contain the chain's most recent link — keeps the sequence of F's contents within a scope totally ordered. Containment of the chain latest is therefore a question about F's own history on B, and that history is already recorded: Lore's per-file-id back-pointer index links each revision that modified F to the previous one in its linear history. No bloom filters, no reachability bitmaps, no per-(branch, file) sparse matrix.

**Content leads, rather than revision identity.** The back-pointer advances on every change to F's tree entry, renames and mode changes included, so "B's most recent F-modifying revision" is not the most recent *content* change and can't be compared to the chain latest directly. Comparing content instead is a single hash comparison for a caught-up branch, reads no history on that path, is immune to rename and metadata noise, and is Goal 4's definition of a content change evaluated directly. A branch that isn't caught up walks the back-pointer history looking for the chain latest's content, and the walk is bounded. Revision numbers grow strictly along every parent edge (`next_revision_number`, in `lore-server/src/grpc/handlers/branch_push.rs`, numbers a revision one above the higher of its parents), and the chain latest names the revision that produced its content, so every revision that carries that content by descent descends from that revision and is numbered above it. Once the walk reaches a revision numbered below the chain latest's, the content can't appear further back by descent, and the branch is behind.

**The bound holds only because the chain latest names the producing revision.** Naming any later revision that merely carries the content breaks it for a branch forked between the two. Suppose branch K edits F to X at revision 1000 and changes other files at 1001 through 1005, and `feat-z` branches from K at 1000, so its first revision is numbered 1001. Suppose the session concluded with the chain naming K's revision 1005. `feat-z` holds X, so it's caught up and acquires, edits F to Y, and pushes its revision 1001. That push's walk meets Y at its first hop, numbered 1001 and so below 1005, and reports `feat-z` proven behind: strict policy refuses a session it granted. Naming 1000, the revision that produced X, finds X at the second hop and places `feat-z` ahead. Naming a catch-up merge on the holder branch, or the merge that carried the work into its parent, fails the same way: an artist who edits F to X on `art` at revision 1001, merges `art` into `main` as `main`'s revision 1101, and edits F again on `art` as its revision 1002 would be behind against 1101, although `art` held X at 1001 throughout. The merge took F unchanged from `art`, so the producing revision is `art`'s 1001, and the walk places `art` ahead.

A walk that exhausts a hop budget denies rather than grants, because it hasn't proven containment, and reports the branch as indeterminate rather than behind; a repository `Owner` or `Admin` can grant past that result, never past a proven behind. In practice it reaches a branch without the lock that sits many edits ahead — an ex-holder after its lock went. The push that concludes a held session is the exception: it's refused only when the walk proves the branch behind, and an exhausted budget passes, because the held lock and the chain latest it was granted against already establish the branch's position. Failing closed there would stop a holder whose session changed the file more often than the budget covers from concluding at all, directly or through a merge to the parent.

Revision identity remains the fallback. Where a revision on the walk can't be read, the walk looks for the chain latest's revision itself under the same bound — stricter, because it misses a branch that reached the same content by another route, so the walk uses it only where content has nothing to compare against.

### Chain advance at push (Goal 2, Goal 8)

**When the chain advances.** The chain latest moves only at a session's conclusion. A session on F runs from acquiring F's lock to concluding or releasing it, and the protocol tracks causality by content, so a session doesn't need to outlive the push that publishes its edit. **A push to the holder branch concludes by default**, whatever its landing revision's parents: it concludes every lock the pusher holds on that branch for a file its session changed, so the chain advances and the lock goes, and a push of several revisions concludes once, at its last. The holder can keep the lock instead (`lore push --keep-lock`, for every file or the listed ones), and the session then spans several pushes: those intermediate pushes publish revisions on the holder branch as normal but **don't** advance the chain latest. Re-acquiring after one's own conclusion is a caught-up comparison, so a session per push costs one acquisition. **A push to any other branch concludes nothing by default**; a merge carrying the holder's work into its parent changes no lock unless the push names files to unlock, as below. The user or tooling chooses when to conclude: at the push (the default), at the merge to the parent (`--unlock` on the merge push), or when the work lands on the scope's final branch, where tooling runs `lore lock release --conclude` to conclude at the holder branch's latest revision. The release a client that predates this proposal already issues is a conclusion too, when the holder branch is caught up or ahead at its latest revision, or behind under chain-advisory (see [Compatibility](#compatibility)); that client's push never concludes. Keeping the lock across pushes produces the "ahead" state described below, where another branch in the scope can have merged and pushed an intermediate revision of the session.

When B pushes a revision C that changes a set of files `{F_1, F_2, …, F_m}`, identified by `file_id` rather than path, that are unmergeable at C or at B's previous latest revision, with `scope_id = scope_of(B)`, the server judges the revision that lands against B's previous latest revision. For a forced push that's the whole change from the old latest revision, and for a fast-forward merge (`lore push --fast-forward-merge`) it's the merge revision the server builds. A forced push that changes an unmergeable file's content needs the lock like any edit.

**The server decides the changed set from the two trees.** It compares the landing revision's tree with B's previous latest revision's, skipping every subtree whose hash is the same on both sides, so the comparison costs in proportion to what changed, and it reuses the walk over both trees that fragment verification already makes. It never trusts the client's own record of a revision's changes: the client writes that record and nothing on the server checks it against the tree, so a gate that read it would land any change the record leaves out, including a revision whose tree holds a file's content from before a concluded edit, which silently reverts that edit on the target.

The push carries a parameter naming which locks it concludes: every lock the pusher holds on the pushed branch for a file its session changed, an explicit list of files, or none. The current CLI sends the first unless the caller keeps the lock (`--keep-lock`) or names files (`--unlock`). On the wire an absent parameter means none, which is what a client that predates this proposal sends.

**On the holder branch, the session belongs to a user.** A push to the holder branch that changes F counts as the session only when it comes from the user the lock entry records, or from one holding the permission to conclude on another user's behalf, a repository `Owner` or `Admin`. A push from any other user is contention, as a push from another branch is; [Enforcement policy](#enforcement-policy-goal-9) states the boundary this draws. A fast-forward merge to the holder branch is a push to the holder branch like any other: it takes the session path under the same user check, and concludes at the revision that produced F's content.

**Carrying the holder's work.** A push that merges the holder's work into its parent goes to a different branch than the one holding the lock. It counts as the holder's session when it carries the holder's work into the parent within the same scope, whoever pushes it: the pushed revision has the holder branch's latest revision as its second parent, or is that revision itself, and F's content at the pushed revision equals its content at the holder branch's latest revision. For a fast-forward merge the condition applies to the revision the server merges in — the client's revision, the built merge's second parent — and F's content at the built merge has to equal its content at the holder branch's latest revision. Such a push concludes nothing unless it names the file to unlock. Only the holder knows whether a session's work is done, so only the holder concludes: a push that names a carried file concludes it when the pusher is the holder, has a repository `Owner` or `Admin` role, or has a repository permission to conclude on another user's behalf. A merge bot either holds that permission or runs as the user who triggered the merge. A carried push from anyone else lands as an intermediate push — the lock stays with the holder and the chain doesn't move, whatever the push asked to unlock — and the push reports those files as not concluded rather than failing. The holder then concludes with `lore lock release --conclude`, at the holder branch's latest revision, under the same check a concluding push gets.

For each `F_i` in `{F_1, …, F_m}`, the server runs the following in parallel — each `F_i`'s per-file work is independent of every other `F_j`:

1. **Validate.** If B holds the lock on `(scope_id, F_i)` and the push comes from the session's user as above, or the push carries the holder's work, the push is on the session path. If another branch holds it, or B holds it for another user, and the push doesn't carry the holder's work, the server refuses the push for contention. If nobody holds it, the server refuses the push: changing an unmergeable file takes its lock, whatever the operation — an edit, a merge, a cherry-pick, a revert, a forced push, or a change that makes the file mergeable or unmergeable. A merge that brings `F_i` to content other than the chain latest's is an edit like any other, so it needs the lock, and a holder can conclude whichever side they chose. Two changes need no lock. A push whose new content for `F_i` already *equals* the chain latest's content is **adoption** rather than an edit: it moves nothing, and it's how a branch that fell behind catches up by merging, even while another branch holds the file. And a push that adds an unmergeable file with no latest entry in the scope — a newly created file, or one no session has concluded there — needs no lock: no concluded content exists for it to collide with, and a file not yet in the branch can't be locked anyway. Such a file gets its latest entry at its first conclusion. A file that has an entry comes into a branch the way any change does: on the chain latest's content it's adoption, and a file the branch deleted comes back under the lock a branch carrying the concluded delete can take ([Content-only chain-link semantics](#content-only-chain-link-semantics-goal-4)).
2. **Chain latest update.** On the session path, the chain latest moves only when this push concludes the session for `F_i`: the pusher can conclude (above), and either the push deletes `F_i` or its parameter covers `F_i` — by default every file the pusher's own session on B changed, and otherwise the files it names. The server advances the branch first and then writes the chain latest — `F_i`'s content at C and the revision that produced it, or, for a delete, a tombstone that keeps `F_i`'s last concluded content and marks it deleted — so no chain latest ever names a revision the branch doesn't carry. If the push modifies `F_i` but keeps the lock and isn't deleting, the chain latest stays where it is and the advance waits for a later push to conclude the session; intermediate revisions sit in the file's normal revision history, but they aren't chain links. Before the repository's backfill completes, a conclusion writes no chain latest at all (see Migration Plan).
3. **Lock release.** If this push concludes the session for `F_i`, remove the lock entry. Otherwise the lock remains held — a push that counts as the session and changes `F_i` renews its lease — and the next such push continues the session without re-acquiring.

No compare-and-swap on the chain latest is needed — the lock is the sole concurrency control on every chain write. The server still checks two things before advancing: that the chain latest is still the value the lock was granted against, which can only fail through a lock-correctness bug and fails loudly; and that C isn't behind it, the push-time half of the causality gate, which catches a branch that acquired under advisory policy or after a force-release. That second check refuses only when the walk proves C behind; an exhausted hop budget passes on this path, for the reason [Why the content check is sound](#why-the-content-check-is-sound) gives.

**Interaction with other branches during a locked session.** While a holder keeps the lock across pushes, a different branch in the same scope that merges the holder branch and pushes holds an *intermediate* revision of the session, content beyond the (unchanged) chain latest. Its push lands as an intermediate push of the session when it carries the holder branch's latest revision, and the server refuses it for contention otherwise. On the chain axis that branch is **ahead**, which grants; it's blocked anyway, because the holder's lock is a contention denial. Once the session concludes past the intermediate it took, the chain latest names content it doesn't hold, and it's behind until it merges. Only the lock holder advances the chain during a session, which is the property the deferral exists for.

**No cross-key atomicity is needed, and Lore has none to offer** — branch advance is a single-key compare-and-swap. A concluding push writes nothing to the lock store before the branch advances; each file's chain write and release follow the advance. A server fault between the two leaves the locks held and the latest entries naming the previous session, which is safe on every axis: no other branch can acquire, and none is misled. The retried push completes the conclusion: a push whose revision already landed still writes the chain latest and releases the lock for each file it concludes, as long as the pusher still holds the lock and the chain hasn't moved, and the CLI retries a concluding push on a transport failure. `lore lock release --conclude` is the manual route. With nobody retrying, the lock stays held until its lease expires, and the reaper releases it without concluding; [Risks and Assumptions](#risks-and-assumptions) records that trade. Per-file work parallelizes naturally: the validation, the chain write, and the release for each `F_i` are independent of every other `F_j`'s.

The above describes the **strict-default behavior**. Under advisory lock-enforcement policy, a push that changes an unmergeable file without holding its lock lands with a warning, the chain stays where it is, and the latest entry records it as an off-protocol edit; under advisory chain-enforcement policy, the push-time check warns instead of refusing a branch it proves behind, and the conclusion it lets through records an off-protocol edit. Both are audit-logged. See Enforcement policy below.

### Optional: collapsing quiescent latest entries

When every branch in a scope holds the chain latest's content for F at its latest revision, the chain is *quiescent*. The latest entry adds no information at that point: any lock attempt would find its branch caught up, write the same chain forward, and update the chain latest in place. Collapsing the entry back to "no entry" is safe and reclaims storage; the next conclusion anywhere in the scope re-establishes the chain latest via the existing first-edit semantics.

Mechanism:

1. Detect consensus for `(scope_id, file_id)`: every branch in the scope holds the chain latest's content for F at its latest revision.
2. Remove the entry, conditionally on its still naming the revision observed in step 1, so a conclusion that advanced the chain latest in between wins; on a failed condition, defer.

Safety follows from the lock being the actual mutex on chain advance, not the latest entry. A removed entry is indistinguishable from one that never existed: first-edit semantics still serialize concurrent acquirers through the lock's insert-if-absent, and the first conclusion after collapse re-establishes the chain latest. A collapse runs only under a lock — the acquiring request's own, with the lazy trigger below — so no other session can be in flight to race it, and the request that collapsed the entry treats it as a first edit when it concludes.

**The first version doesn't build this.** Its consensus check reads one answer per branch per file, the one operation in the design that scales with `branches × files`, which Goal 3 forbids. If it's built, the trigger is lazy at acquisition rather than a sweep: that request already holds the lock and has the entry in hand, so the only missing input is whether every other branch in the scope agrees, which a scope-level counter can answer without the per-branch fan-out.

This optimization is layered, not load-bearing: the proposal is correct without it. Its benefit rests on an assumption this proposal hasn't measured, that most files spend most of their time in consensus. Where that holds, storage tracks live *divergent* (scope, file) pairs rather than every (scope, file) pair edited in the scope; where it doesn't, the collapse reclaims little.

Stale or abandoned branches keep it from firing: the consensus check fails while one forgotten branch in the scope lags behind. A built version therefore filters its branch set to active branches — modified within some window, or whose latest revision isn't reachable from another live branch — and leaves abandoned branches to a separate cleanup.

### Lock state — required contract (Goal 1)

What this LEP mandates is the contract a store must satisfy to implement the protocol. The lock and the latest entry for a `(scope, file)` are used together on every path that matters — an acquisition reserves the lock and reads the chain latest, a conclusion writes the chain latest and releases the lock — so **one store holds both**, and an implementation can keep them in one record. Storage choice — a dedicated table, the server's in-memory `local` store, or any other conforming store — is downstream of this LEP.

**Key shape.** The protocol identifies a lock by `(scope_id, file_id)`. The chain invariant depends on two branches in the same scope contending on *the same* key when they want to lock the same file. Branch is *not* part of the key — it appears in the value (below). The existing lock store keys on `(repository, branch, path hash)` with branch in the key (`LockKey`, in `lore-server/src/lock/store.rs`, over the hash of the path that `assemble_resource_for_path`, in `lore-revision/src/lock/util.rs`, takes), which is why this protocol adds a store rather than re-keying that one; the existing lock service is later served from the new store, for every lock it takes, including locks on mergeable files, which then contend per scope like any other.

**Required operations.**

- **Reserve** — insert-if-absent per key, tagged with the acquisition it belongs to, returning the key's latest entry in the same operation. Reservations are independent per key, so an acquisition has no width limit; it's all-or-nothing because a reservation can't be pushed against until it's confirmed, not because the store offers a transaction.
- **Confirm and cancel** — promote an acquisition's reservations to held, or drop them, addressed by the keys the acquisition reserved.
- **Move** — at confirm, transfer a held key to the acquisition's holder branch, conditional on the key's current holder branch, user, and session, keeping the chain latest the lock was granted against. The key is never free between the two holders.
- **Renew** — extend the lease of a set of held keys.
- **Conditional release** of a set of keys, by the holder, with or without concluding, or by an administrator's force-release.
- **Holder read** for a set of keys, returning each current holder or absent. Used by push-time validation and by lock-denial messaging.
- **Holder enumeration** — every lock one user holds, for an administrator's bulk force-release, and every lock one branch holds, for the branch-archive precondition.
- **Chain latest read and write**, including an absent-only write for backfill, and the backfill-completion marker, kept beside the entries.
- **Scope enumeration** — every latest entry in a scope, for purge and capacity reporting.

**Authorization.** An acquisition takes the permission a push to the branch it names takes — write access for an unprotected branch, the push-protected permission for a protected one — on both lock services, and that branch becomes the holder branch. Other branches in the scope don't enter the check. On the holder branch, a push that changes the file, a repeated acquisition, and the lease renewal a push gives count as the session only from the user the lock entry records, or from one holding the conclude-on-behalf permission, `Owner` or `Admin`. A release has to come from the holder. Moving a lock to another branch has to come from the user the lock entry records, and takes the permission a push to the branch it moves to takes. Concluding — a push that concludes, or a concluding release — has to come from the holder, a repository `Owner` or `Admin`, or a user with the permission to conclude on another user's behalf, checked against the user the lock entry records. Force-release, of one lock or of every lock one user holds, takes `Owner` or `Admin`, and so does granting past an indeterminate result.

**Value contract.** A lock entry associates the held key with the holder's `branch_id` and user, as today's lock entries do, plus whether it's confirmed, the chain latest it was granted against, and its lease expiry. A lock taken through the existing lock service also records F's content at the holder branch when the lock was granted, so its release can tell whether the branch changed the file. A latest entry carries F's content at the conclusion and the revision that produced it, whether the session concluded by deleting F, and the off-protocol marker when one is set. Further fields are implementation choice.

**Concurrency contract.** Reservation, move, and release must be atomic with respect to each other and to themselves, and a reservation atomic with the latest entry it returns; the protocol relies on the lock being a true mutex for the chain latest it pins.

**The lease is in the contract, at its minimum.** An unconfirmed reservation abandoned by a crashed acquirer is reclaimed only by expiry, and a held lock whose holder never comes back is released only by expiry or by an administrator — so leaving leases out would leave the protocol's crash behavior undefined. The contract requires server-owned expiry, short for an unconfirmed reservation and long for a held lock, and a reaper that releases an expired lock without concluding. A held lock's lease renews from the holder's own work on the file: marking it dirty (`lore file dirty`, or an editor's change notification) and committing a change to it renew the lease from the client, coalesced into at most one renewal call every few minutes and replayed after reconnecting, and the server renews it when a push that counts as the session changes the file and keeps the lock. The lease can therefore be days long, and expiry reaps only sessions that are idle. A lock taken through the existing lock service, whose clients have no renewal call, gets a longer lease, renewed by any call its owner makes to that service and by a push that counts as its session changing the file.

**Out of scope.** Renewal interval, sweep cadence, on-disk representation, the query surface beyond what the operations above require, and any rich-predicate lookups — implementation concerns that don't change the chain protocol.

### Enforcement policy (Goal 9)

The two primitives this proposal introduces are informational at the protocol level: the **lock entry** carries the signal "this file *is* being modified by branch B right now," and the **chain latest** carries the signal "this file *has* been modified up through revision R; your branch is at R'." How strictly the server gates operations on those signals is a separate concern — a repository policy, not a protocol property. The mechanism is two repository-metadata keys, one per axis, each `strict` by default; setting either to `advisory` takes a repository `Owner` or `Admin`, and the server records the change as a repository audit event.

The server consults both keys on every push and acquisition, and a request never waits on a metadata read to learn its policy. A change takes effect at once on the server that took it, and on every other server within a bound the deployment configures, 30 seconds by default; how a server meets that bound is the implementation's choice. Until then servers can disagree: one can refuse a push that another lands with a warning, so an operator relaxing a repository to advisory during an incident sees it apply everywhere only once the bound has passed. Richer alternatives remain possible extensions. This proposal rejects a per-scope override in particular, because a scope is a unit of causality rather than a security boundary, and varying strictness by scope would make a file's protection depend on which branch a user started from.

The protocol exposes two independent strictness axes:

- **Lock enforcement policy.** Under **lock-strict** (the default), the push handler refuses a push that changes an unmergeable file without holding its lock, or that collides with a lock another branch holds, or that the pushing branch holds for another user — the cases step 1 of Chain advance at push lists, with adoption and adding a file as the two that need no lock. Lock acquisition still serializes at the lock store regardless of policy. Under **lock-advisory**, the push handler lands such a push with a warning, leaves the chain where it is, records the edit on the latest entry as off-protocol, and audit-logs it. The lock entry continues to surface "who is editing" for coordination; what advisory mode disables is the server's refusal of unlocked pushes. The lock axis depends on chain state too, because adoption does: until the repository's backfill completes there are no latest entries, so no push can be adoption, and a strict lock axis would refuse every catch-up merge for contention while any branch held the file. It therefore acts as advisory until backfill completes, whatever its key says, as the chain axis does.
- **Chain enforcement policy.** Under **chain-strict** (the default), lock acquisition denies a requester that's behind on F (chain-behind denial) — not merely one whose content differs, since an ahead branch is granted — and push validation refuses a concluding push the walk proves behind the current chain latest. Under **chain-advisory**, both points emit warnings and audit-log but proceed. The chain latest continues to surface "is your view current" for staleness display; what advisory mode disables is the server's refusal to advance a divergent chain. The chain axis is strict only once the repository's backfill has completed: before then there's no chain to judge against, every acquisition is a first edit, and the axis acts as advisory whatever its key says (see Migration Plan).

The two axes combine independently: a repository can run lock-strict + chain-strict (the safety-maximizing default), lock-strict + chain-advisory (every edit takes a lock, but a stale acquisition is granted with a warning), lock-advisory + chain-strict (an unlocked push lands with a warning, but a lock or a conclusion still needs a branch that isn't behind), or both advisory (the primitives become pure signals; closest to Git LFS's posture today).

**Branch and user together decide contention and the session path.** On the holder branch, a push that changes a locked file, an acquisition of it, and the lease renewal a push gives count as the session only when they come from the user the lock entry records, or from one holding the conclude-on-behalf permission, `Owner` or `Admin`. Another user's change to the file is contention under lock-strict and an off-protocol edit under lock-advisory, and its acquisition is denied for contention. The carried-work rule doesn't change: it checks content, so a merge that carries someone else's work into another branch lands, and concludes nothing unless it names files to unlock. Handing a file over in the middle of a session on a shared branch therefore needs the holder to end the session — a push does by default — or an administrator's force-release, and a tool that pushes as its own user takes its own lock or holds the conclude-on-behalf permission. Moving a lock to another branch keeps its user, so it hands the file to nobody else.

The user is the finest distinction the server can verify, and that sets the boundary. One user working on several machines or instances passes the user check on each, and the server can't tell them apart. That case stays contained: a branch's pushes land one at a time, each on the branch's latest revision, so the holder's second push has to merge the first, an unmergeable file conflicts explicitly, and history keeps both sides.

**Both axes apply to every client**, including one that predates this proposal, because each check sits on a call such a client already makes. Lock enforcement asks for a convention — take a lock before changing an unmergeable file — which a client can follow without knowing anything about chains, scopes, or causality, and which the existing lock API already expresses. Chain enforcement reaches an old client through the same calls: its lock request runs the caught-up check, and a branch that's behind receives a failed lock whose message names what to merge; its release concludes the session when the holder branch is caught up or ahead at its latest revision, and otherwise, under chain-strict, releases without moving the chain, recording an off-protocol edit if the branch changed the file while it held the lock. A client holding a lock while behind, and publishing a divergent edit, is therefore something only advisory policy accepts. The server audit-logs every operation that proceeded under advisory policy with the same fields the strict-denial path would have emitted, plus the policy that accepted it — so operators can see what strict policy would have denied and how often the relaxed policy is being relied upon.

Advisory mode preserves the protocol's chain-tracking machinery as a source of truth: the chain latest still advances at each conclusion, the lock entries still come and go, and the audit trail still records who did what. What changes is only the server's response to off-protocol intent — *deny* under strict, *warn and record* under advisory. Either way, a client operates within the strictness the repository has set: it can't skip the checks, and forging the file-history index they read gains it nothing a lock holder doesn't already have (see [Security Considerations](#security-considerations)).

### Administrative force-unlock

The protocol exposes an admin-only operation that forcibly releases a held lock without going through the normal commit-and-push cycle. This is the operational escape hatch for stuck or abandoned sessions — a workstation that crashed mid-edit, an account that left the team, an automated process that took a lock and never released it.

The mechanism follows from the deferred advance: a session's chain latest moves only when its holder *concludes* it (Chain advance at push, step 2), so force-releasing a held lock removes the lock entry and the chain latest stays where it is. This makes force-unlock a lock-release operation rather than an undo of the session: the ex-holder's branch is ahead of the chain, so it can re-acquire and conclude the very session that was force-released. That's the wanted behavior for the case force-unlock exists for — a zombie lock from a crashed workstation — and it means deliberate abandonment needs a different instrument, such as branch protection. Any intermediate revisions the holder pushed during the session — revisions that modified the file while keeping the lock — remain in the holder's branch revision history as ordinary revisions, but the chain latest still points at the revision from the *previous* concluded session. Every other branch is judged against that, so the in-flight content doesn't become the chain's unless the ex-holder concludes it.

The force-released branch is **ahead** of the chain latest for that file: it holds that content and edits beyond it. Its next acquisition is granted, unless another branch took the lock first, and the session it then concludes is the one an admin force-released — which is how a user whose workstation crashed comes back and finishes. A branch so far ahead that the walk runs out of budget is denied as indeterminate, and an admin can grant it past that. If another branch acquired F in between and concluded first, the ex-holder is behind that chain latest and merges before continuing, like any other branch.

Force-unlock requires a repository `Owner` or `Admin` — the same elevation that releasing another user's lock takes today (`is_elevated`, in `lore-server/src/grpc/lock_service.rs`). That existing release is a force-unlock too: when an `Owner` or `Admin` releases another user's lock through the existing lock service, the lock goes, the chain latest stays where it is, and nothing concludes. An administrator can also release every lock one user holds with one command, for an account that left the team or a caller holding locks to block others. The server records every force-unlock in the chain-advance audit trail (see Observability under Non-Functional Considerations) with the admin user, the target `(scope_id, file_id)`, the prior holder's `branch_id`, and the chain latest the operation left unchanged — so the operation is traceable even though it bypasses the normal commit-and-push flow.

Force-unlock answers one operational need — zombie locks — and deliberately not a second. It doesn't abandon a session: since the ex-holder can re-acquire and conclude, an admin who needs a holder's work kept out of the chain uses branch protection or revokes write access instead. Recording the abandoned revision on the latest entry, and treating a branch whose only route to being ahead runs through it as behind, would restore that semantic at the cost of a check on the acquisition path to serve a rare case; this proposal doesn't add it.

### Identity by file_id and scope_id (Goal 5, Goal 7)

All cross-branch state — latest entries, lock entries, caches — keys on `Hash(scope_id, file_id)`, never on path. Rename and move don't disturb file identity. B1 may see F at `assets/old/foo.uasset` and B2 at `assets/new/foo.uasset`; if both are in the same scope, both derive the same key and contend against the same chain latest; if in different scopes, they derive different keys and sit on independent chains. Scope lookup is a single per-branch cached value.

**A lock belongs to the repository that owns the file, not the one the caller reached it through.** Lore links repositories into one another, and a linked repository can be mounted at more than one path and by more than one parent. Identifying a lock by the mount path would give the same file a different identity per mount, so two people editing it would never contend — and today's path-keyed locks do exactly that, in the parent's partition rather than the owning one. The client keys a lock on a hash of the path it resolved in the outer repository (`assemble_resource_for_path`, in `lore-revision/src/lock/util.rs`, called from `lore-revision/src/lock/file/acquire.rs`), and the lock service takes the repository from the request's metadata (`get_repository`, in `lore-server/src/grpc/lock_service.rs`). Keying on `file_id` removes the problem by construction: the identifier is allocated in the owning repository and travels with the node, so every mount derives the same key. Crossing a link means crossing into that repository's state, and the scope resolves there too, against the linked repository's own branches.

### Unmergeability

Unmergeability is the property that puts a file under the lock protocol: changing an unmergeable file takes its lock, and its concluded edits form its chain. The repository decides which files have it. How a repository defines, stores, and loads that set is the implementation's choice; this proposal states only the requirement that choice has to meet.

**The definition has to be cheap to consult.** The server decides unmergeability on every push, for every file the push changes, on both sides of the change. The repository therefore needs a way to define, store, and load which files are unmergeable that costs no more than a lookup per file on the push path, with no cost that grows with the depth of the tree or the size of the repository. The definition also has to load cheaply per request.

**A push decides unmergeability on both sides of each change** — at the pushed revision and at the branch's previous latest revision — and a file unmergeable on either side is gated. Changes that make a file mergeable or unmergeable, a rename among them, therefore need the lock while the file is unmergeable on either side, though none moves the chain. Otherwise three pushes — make the file mergeable, edit it, make it unmergeable again — would edit an unmergeable file outside the protocol. A holder can still make a file mergeable on their branch under the lock, deliberately.

**Who can change the definition depends on how the change arrives.** A change to the definition that a push carries needs the lock like an edit, through the two-sided check. A change made outside a push, as repository configuration, takes a repository `Owner` or `Admin`, like the enforcement keys, because making a file mergeable drops its protection.

**A file that becomes unmergeable after backfill gets a backfill of its own.** A change to the definition that makes files unmergeable covers files that nothing tracked while they were mergeable, so they already sit at divergent content across branches. The change records which files it made unmergeable, leaving out any that already has a chain in the scope, whose entries are correct again once it's unmergeable; backfill runs over them as the [Migration Plan](#migration-plan) describes for the whole repository, and until that completes no conclusion writes their chain and both axes act as advisory for them, as they do for a repository whose backfill hasn't completed: with no entries, no push of theirs can be adoption. Seeding their chains from whichever branch locks each first stays rejected, for the reason the Migration Plan gives.

### Content-only chain-link semantics (Goal 4)

Only a concluded change to an unmergeable file's *content* (the BLAKE3 hash on its leaf node in the Merkle tree) advances the chain for the scope the push happens in. Metadata-only edits (mode, timestamps, extended attributes) and path-of-record changes (rename, move) produce tree entries but never advance the chain, and they need no lock — except a change that makes the file mergeable or unmergeable, which needs the lock as [Unmergeability](#unmergeability) describes. Cross-branch path divergence is resolved at merge time via Lore's normal tree-merge, the same way it works for mergeable files: `file_id` is stable across renames, so a merge sees the same file at two paths and picks one, content-consistency already enforced by the chain on the orthogonal content axis. Copy creates a new `file_id` and a new chain (in the active scope); F's chain in any scope is untouched, and the copy, like any added file, needs no lock until it's edited.

Delete concludes the session to a **tombstone** in its scope: the latest entry for `Hash(scope_id, file_id)` keeps the file's last concluded content and marks it deleted, rather than disappearing. A branch that still has F — branched from before the delete — is judged against that content as if the delete hadn't happened: caught up or ahead is granted, behind is denied, so a stale copy of F can't come back as a first edit. A branch that carries the concluded delete, by its own push or by a merge, can lock the deleted file, judged caught up, so the push that brings the file back can conclude; any other branch without the file can't lock it. A conclusion on a branch that still has the file makes the chain live again, and that branch's later merge against the delete is the delete-versus-edit conflict below. First-edit semantics apply only where no entry has ever existed in the scope, or after a scope purge.

The server writes the tombstone when a session concludes a delete of F under the lock — at the push that deletes it, or, for an old client, whose push never concludes, at its release — not when a branch's latest revision lacks F by other means, which is meaningless under free branching. A feature branch that concludes a delete of F turns the chain latest in its scope into a tombstone even if other branches in the same scope still have F, and those branches go on being judged against F's last concluded content. The theoretical safety property: a delete-vs-edit conflict between two branches always has a no-loss resolution because the user can elect to keep the edit (the delete carries no content state to discard, only an intent to remove). Resolving in favor of the edit preserves all work; resolving in favor of the delete is a deliberate user choice to discard work. Either way, the conflict has a defined outcome and no work is lost without explicit user direction. Deletions and resurrections in one scope are independent of any other scope's chain — F may be deleted on a release scope while remaining alive (and editable) on main's scope.

### Cross-scope merges

A merge that pulls revisions from a branch in scope A into a branch in scope B is the one operation where scope boundaries are intentionally crossed. When the merge brings in revisions that touch an unmergeable file F, the merge produces a tree entry for F in scope B that is **not** derived from scope B's existing chain. The proposal treats this as an edit in scope B on the same terms as any edit there: it needs a held lock on F in scope B (the `(scope_id, file_id)` key for the target scope), and the session's conclusion advances B's chain. The server doesn't consult the source-scope chain. The cross-scope merge is a fresh chain link in the target scope, regardless of what F's history looked like in the source scope.

This preserves the per-scope chain invariant (every advance is a successor of the prior chain latest in its own scope) and keeps cross-scope semantics to one rule: scopes never share chain state, only branch DAG ancestry. The cost is that backporting an unmergeable-file fix from main to a release scope advances the release scope's chain exactly as a fresh edit there would — under a lock held in the release scope — with the merger choosing to apply the change, which is the correct user-facing model.

### Lock-denial error surface (Goal 6)

The denial carries the chain latest's revision and the scope, `(latest_revision, scope_id)`; the client resolves the branch, author, and timestamp from revision metadata when it renders the message. The CLI presents:

```
error: cannot acquire lock on assets/hero.uasset — branch is behind on this file in scope 'main'
  chain latest: 9f3a...c12d (created on feature/lighting, 2026-05-14)
  scope:        main
  suggested:    lore branch merge feature/lighting
                then push the merge — it needs no lock
```

The remedy for behind is always a merge followed by a push, never a local sync. The check runs against the branch's latest revision as the server holds it, so moving a local anchor changes nothing it looks at; the branch itself has to take the content in and publish it. That push is adoption and needs no lock, which keeps the remedy available even while someone else holds the file.

When the branch the chain latest's revision was created on has since been archived, the message says so and suggests merging it by id (`lore branch merge <branch-id>`): an archived branch keeps its id, history, and latest revision, so it stays mergeable.

An indeterminate denial — the walk ran out of budget before it could place the branch — says so rather than implying the branch is behind, and names the two ways out: ask a repository `Owner` or `Admin` to grant past it, or adopt the chain's content. Merging the chain latest in, the remedy for behind, does nothing for a branch that already contains it.

A file the requester's own user holds on another branch in the scope is contention like any other, and the message suggests moving the lock with `lore lock acquire --from <branch>`.

The client derives the branch it names and the scope's display name from revision and scope metadata, not from denormalized fields in the latest entry.

## Compatibility

- **Wire format** — Two values join the mutable store's `KeyType`, `ScopeMetadata` at discriminant 8 and `ScopeId` at 9 (`lore-base/src/types/store_types.rs`), and they travel in mutable-store messages like any other key type. A peer that predates them can't decode either: its `KeyType::try_from` rejects an unknown discriminant, so it reports an error rather than misreading the key as another type. Only the server writes them, through the scope RPCs, and the generic mutable-store write path refuses both from clients, as it already refuses repository metadata, branch metadata, and branch latest pointers (`DISALLOWED_KEY_TYPES`, in `lore-server/src/protocol/storage/mutable_store_handler.rs`), so no client sends one to a server that can't decode it. A new peer decodes everything an old one sends. Message encodings, framings, and content-address derivations are otherwise unchanged; the fields existing messages gain are listed under Client/server protocols.
- **Client/server protocols** — A new versioned lock service alongside the existing one, streaming rather than unary for acquisition, release, renewal, and status, since [multi-file acquisition](#multi-file-acquisition-goal-1-goal-3) needs one consistent view of the branch and no size ceiling. An acquisition can also name the branch its locks move from ([Moving a lock to another branch](#moving-a-lock-to-another-branch-goal-1)). Existing messages only gain fields: `causal_locks` on the environment service's `Config` message, an optional `scope` on `BranchCreateRequest`, `unlock_mode` and `unlock_files`, fields 5 and 6, on `BranchPushRequest`, and `lock_results`, field 5, on `BranchPushResponse` (all three in `lore-proto/proto/lore/revision/v1/revision.proto`). The existing lock service keeps its wire shape permanently and is served from the same state, so both surfaces see one set of locks; what changes in its behavior is listed under *Behavior for clients that opt into nothing* below. A client discovers the new service through an explicit `causal_locks` field on the environment service's `Config` message (`lore-proto/proto/lore/environment/v1/environment.proto`) rather than through the lock endpoint, because an empty endpoint URL already means "use the URL you were configured with," as the comment on that file's per-service endpoint URLs states. An old server leaves the field false, and a new client then falls back to the existing service and warns once per command that causal protection is off. So an old client against a new server and a new client against an old server both keep working with no negotiation to add.

  Scope management is a set of new RPCs on the existing repository service, and branch creation gains an optional field naming the new branch's scope. Only the server writes scope state, so a client never sends a new key type to a server that can't decode it: an old server answers the scope RPCs with "unimplemented." It ignores the branch-creation field, though, as protocol buffers ignore any field a reader doesn't know, so a branch created with an explicit scope against an old server lands in the default scope — and stays there, since scope is fixed at creation. This proposal accepts that rather than guarding it: scopes, and the causal locks built on them, need an updated server, and the release notes say so.

  A push reports what the lock protocol did to each unmergeable file in a form a client acts on rather than parses. A refused push fails with `FailedPrecondition` carrying a refusal detail per file — no lock held, contention naming the holding branch and user, or behind naming the chain latest's revision and scope — in the rich error model (AIP-193) that `lore-proto/proto/lore/error/v1/error.proto` defines, an encoding no client mistakes for the status details it reads by length; and a push that lands returns a per-file result: concluded, with the revision the chain records; kept; not concluded, and why; or landed off-protocol. A store the server can't reach refuses the whole push with `UNAVAILABLE`. A client that predates these fields reads neither, so the server also writes the same information as text into the push response's free-form message and the refusal's status message. Client error codes `LORE_ERROR_CODE_LOCK_REQUIRED`, `LORE_ERROR_CODE_LOCK_CONTENTION`, and `LORE_ERROR_CODE_LOCK_INDETERMINATE` join `LORE_ERROR_CODE_LOCK_CHAIN_BEHIND`, and the C API emits one event per file for a push's lock results.

  Push gains a validation step for unmergeable-file chain latest and lock state (failure modes: no lock held, another branch or another user holding the lock, a concluding revision that's behind) and a parameter controlling which locks the push concludes. **On the wire the parameter defaults to concluding nothing**, which is what an old client's push means, so an old client's push never concludes and its release concludes its session instead. The new CLI sends the parameter on every push: by default, concluding the locks the pushing user holds on the pushed branch for the files its session changed, and keeping them under `--keep-lock`.
- **On-disk format** — New server-side state; this proposal itself changes no repository data. Scope metadata and scope-name lookup add two `KeyType`s to Lore's existing mutable store (`KeyType::ScopeMetadata`, `KeyType::ScopeId`, at discriminants 8 and 9 of the enum in `lore-base/src/types/store_types.rs`, which an old server's decoder rejects rather than misreads), mirroring the existing branch storage pattern; scopes go there because listing them is what the mutable store uniquely offers. Latest entries and lock state live together in a store satisfying the lock contract specified in Proposed Design — a dedicated table, the server's in-memory `local` store, or another conforming store; the choice is downstream of this LEP. Where the repository's definition of unmergeable files lives is downstream too, within the requirement [Unmergeability](#unmergeability) states. The repository's Merkle tree layout, fragment encoding, branch latest pointers, and revision-record format are otherwise unchanged.
- **CLI and public API** — additions and behavior changes by command family:
  - **`lore lock`**
    - `lore lock acquire` decides each file separately inside one acquisition and, by default, cancels the whole acquisition on any denial; `--partial` keeps what was granted instead. Each file's outcome on the wire is one of `GRANTED`, `CONTENTION`, `CHAIN_BEHIND`, `INDETERMINATE`, `NOT_IN_BRANCH`, and `NOT_UNMERGEABLE`, and arrives as a result inside the acquisition rather than as a failed call.
    - A branch that's behind on the file in its scope is `CHAIN_BEHIND`, which the CLI and the library surface as `LORE_ERROR_CODE_LOCK_CHAIN_BEHIND`, with a payload naming the chain latest's revision and `scope_id`. A branch that's *ahead* is granted, not denied.
    - A file someone else holds is `CONTENTION`, surfaced as `LORE_ERROR_CODE_LOCK_CONTENTION`, naming the holding branch and its user. Another user's lock on the requester's own branch reports the same way, with that branch as the holder.
    - A branch the walk can't place is `INDETERMINATE`, surfaced as `LORE_ERROR_CODE_LOCK_INDETERMINATE`. A repository `Owner` or `Admin` grants past it with `--override-indeterminate`, adding `--owner <user>` to hold the lock for the user who asked, so that user's own push concludes the session; a proven behind stays denied whatever the role.
    - Acquiring takes the permission a push to the branch takes.
    - `lore lock acquire --from <branch> [paths]` moves each lock `<branch>` holds for the caller to the current branch, and acquires any listed file `<branch>` doesn't hold, under the checks any acquisition makes; with no paths it moves every lock the caller holds on `<branch>`. Each file's result says whether it moved, and the command warns about a moved file whose content on `<branch>` matches neither the chain latest nor the current branch.
    - `lore lock release` releases without advancing the chain. It warns when the holder branch has published edits to the file that the chain latest doesn't hold — after a release, another branch can overtake them — and points at `--conclude` to conclude instead.
    - `lore lock release --conclude <paths>` concludes the holder's session at the holder branch's latest revision, when that branch is caught up or ahead there. Otherwise, under chain-strict, it keeps the lock and reports the file as behind, naming what to merge; under chain-advisory it concludes with a warning, as a concluding push does.
    - `lore lock release --force --holder <user>` releases every lock one user holds, for a repository `Owner` or `Admin`.
    - `lore push` concludes by default: every lock the pushing user holds on the pushed branch, for a file its session changed. `--keep-lock` keeps every lock, or the listed paths, instead. `--unlock` names files to conclude — all the push changes, or the listed paths — which is how a push that carries another branch's session into its parent concludes it. The CLI retries a concluding push on a transport failure.
    - `lore file dirty` and `lore commit` renew the lease of a locked file they touch.
  - **Libraries.** The C API (`lore-capi/lore.h`, implemented in `lore/src/interface.rs`) already exposes lock acquisition, status, query, and release (`lore_lock_file_acquire`, `lore_lock_file_status`, `lore_lock_file_query`, `lore_lock_file_release`, each with an `_async` form) and branch push (`lore_branch_push`), and it follows the CLI. `lore_branch_push` concludes by default as `lore push` does, and its arguments gain the keep-lock and unlock choices; release gains conclude; acquire gains partial acquisition, the indeterminate override with the owner it acquires for, and the branch to move locks from. Each new flag is a `u8`, as the C API's other booleans are, and a caller that sets none of them gets the CLI's defaults. That changes what an existing integration's push does: it concludes the locks its user holds on the pushed branch for files the session changed, where today a push releases nothing.
  - **`lore repository`**
    - The two enforcement keys are repository metadata (see *Repository metadata* below), so `lore repository metadata set` and `lore repository metadata clear` write them, as they write any repository metadata key (`lore-client/src/cli/commands/repository.rs`). The server refuses a change to either from a caller without the role *Repository metadata* names.
    - `lore repository info` displays both enforcement axes, and the share of pushes still arriving on the push path that clients predating this proposal use.
  - **`lore scope` (new subcommand family)**
    - `lore scope create <name>` — creates a scope, returns the new `scope_id`. Refuses the reserved name `default`.
    - `lore scope list` — lists active scopes; `--all` includes archived.
    - `lore scope info <scope-id|name>` — displays scope metadata.
    - `lore scope rename <scope-id> <new-name>` — changes the display name. The default scope takes no lifecycle verb, this one included.
    - `lore scope archive <scope-id>` — drops the `scope_name → scope_id` mapping. `scope_id`, metadata, latest entries, and branch references persist. Refused for the default scope.
    - `lore scope restore <scope-id> <name>` — reinstates a name mapping for an archived scope.
    - `lore scope purge <scope-id>` — permanent removal; clears metadata and latest entries too. Refused while any live branch still names the scope, and always for the default scope.
    - Creating a scope needs write access to the repository; rename, archive, and restore need repository administration or the scope's creator; purge needs repository administration.
  - **`lore branch`**
    - `lore branch create` gains a `--scope <scope-id|name>` flag to assign the new branch into an existing, unarchived scope; without the flag the new branch inherits its parent's scope. Against a server that predates scopes the flag has no effect, and the branch joins the default scope.
    - `lore branch info` output includes the branch's `scope_id` and the scope's display name.
    - `lore branch create` and `lore branch switch` name each file whose uncommitted edits they carry while the branch they leave holds its lock for the caller, and point at `lore lock acquire --from`. Neither moves a lock.
    - `lore branch archive` gains a precondition: refused while the branch holds locks, until the holder releases or concludes them or an administrator force-releases them. The branch-delete RPC, which archives, has the same precondition.
    - `lore branch merge` runs a pre-flight before it changes anything: a best-effort acquisition over the unmergeable files the merge touches, reported by outcome — granted, contended and by whom, behind and against what — followed by one confirmation. `--auto-lock` proceeds without asking when every file is grantable.
    - `lore branch merge` takes the same `--keep-lock` and `--unlock` flags as `lore push`. Its push goes to the parent, which isn't the holder branch, so by default it concludes nothing.
- **Repository metadata** — two keys join the repository's metadata:
  - `lock-enforcement` and `chain-enforcement`, each `strict` or `advisory`. An absent key reads as `strict`.
  - Setting either takes a repository `Owner` or `Admin`, or write access on a server running without authentication, and the server records each change as a repository audit event. Neither enforcement key takes effect before the repository's backfill completes, and neither has any effect on a server configured with no lock store.
- **Server configuration** — two fleet-wide settings, each off by default, turn on phases 4 and 5, which change what clients see; phase 6 takes no setting, because its deploy is what turns enforcement on (see [Migration Plan](#migration-plan)):
  - `causal_locks` makes the environment service's `Config` report the new lock service, so new clients use it.
  - `lock_bridge` serves the existing lock service from the new store, so both surfaces see one set of locks.
  - Neither works per server: servers that disagree give clients two answers, and a fleet only partly on `lock_bridge` grants one lock to two people. An operator turns each on once the whole fleet carries its phase, and back to roll that phase back — `lock_bridge` a step at a time, through dual-read.
- **Lock notifications** — subscribers to today's `resource_locked` and `resource_unlocked` notifications, which the existing lock service publishes (`lore-server/src/grpc/lock_service.rs`), keep receiving them in their existing shape: a branch, a path hash, and a path. The new lock service emits both too. For a lock in the new store, their path is the one inside the repository that owns the file, rebuilt from the node the lock records, rather than a mount path, and a multi-file acquisition sends one notification carrying every file. Their branch is the holder branch, and `resource_unlocked` fires whenever a lock goes: a release, a conclusion at a push or a release, a force-release, or a lease expiry. A move sends `resource_unlocked` for the branch the lock left and `resource_locked` for the branch it moved to. The sender publishes per repository, so subscribers keep seeing every branch's locks. Two notifications join them, carrying ids rather than paths: `latest_advanced`, naming the repository, scope, file, and revision when a chain advances, and `scope_changed`, naming the repository, scope, and lifecycle verb.
- **Behavior for clients that opt into nothing** — these changes reach a client, script, or tool that uses none of the additions above:
  - Locks become per-scope rather than per-branch, so two branches in one scope that could each hold the same path independently contend. That includes locks on mergeable files, which stop other branches in the scope from locking the file but never refuse a push.
  - A lock belongs to the user who took it as well as its branch. On that branch, another user's push that changes the file is refused under lock-strict, as contention, unless that user holds the conclude-on-behalf permission, `Owner` or `Admin`.
  - Under lock-strict, a push that changes an unmergeable file's content without holding its lock is refused, whether a person, a tool, or an old client made it, and so is an unlocked push that makes a file mergeable or unmergeable. Rollout runs advisory first, and its off-protocol records show which tools still don't lock.
  - A lock request from a branch that's behind on the file is refused, and an old client receives it as a failed lock whose message names what to merge.
  - A lock on a protected branch takes the push-protected permission; an old client's request without it is refused.
  - A lock on a file that isn't in the branch on the server — staged or committed but not yet pushed — or on a resource that isn't a file is refused, with a message saying to lock after the first push.
  - An old client's release concludes its session: for each released unmergeable file whose content at the holder branch's latest revision differs from the chain latest, the server advances the chain there when that branch is caught up or ahead, and otherwise, under chain-strict, releases without moving the chain. Under chain-advisory a behind release concludes too, and the audit trail records it.
  - An `Owner` or `Admin` releasing another user's lock, which the existing lock service accepts today, force-releases it: the lock goes, the chain latest stays where it is, and nothing concludes.
  - A lock taken through the existing lock service gets a 30-day lease, renewed by any call its owner makes to that service and by a push that counts as its session changing the file. The server releases a lock left untouched for the whole lease without concluding.
  - Archiving a branch that holds locks is refused.
  - A lock on a file reached through a link is held in the repository that owns the file, under the path there: an old client reads back that path rather than the mount path it typed, and two locks it took on one file through two mount paths become one, with each such pair reported during the bridge's migration.

## Non-Functional Considerations

- **Concurrency** — The exclusive lock is the sole mutex on chain latest writes: only a holder's conclusion writes the chain, so no chain write is conditional except backfill's absent-only one. Lock acquisition uses the store's insert-if-absent reservation. Concurrent lock attempts on the same `(scope_id, file_id)` serialize at the store, and two acquisitions wanting overlapping sets converge because the younger transaction yields on a conflict, by the time-ordered id the server assigns; clients present entries in one consistent key order, which the server verifies, to bound the work a yield throws away. Moving a lock to another branch is one conditional write per file at confirm, taken only while the source branch still holds the lock in the same session, so a conclusion on the source branch in the meantime wins and the move reports the file as not moved. Concurrent push validations across files parallelize naturally — each key is independent. Multi-file pushes need no cross-key atomicity: each file's chain write and release follow the branch advance, and a push interrupted between them leaves its locks held until the retried push or the holder concludes.
- **Memory** — A latest entry is a revision hash and a content hash, plus, on a tombstone, the revision that concluded the delete; a lock entry is the holder branch, its user, and lease fields. Latest storage is the sum over scopes of the files concluded or seeded by backfill in each, tombstones included — not `live unmergeable files × scopes`, since a scope accrues an entry only for a file concluded in it or seeded there by backfill. Neither kind of entry shares the mutable store's key space. Acquisition of a caught-up file is constant memory per entry; a walk holds the blocks it reads, and walking a batch in node-block order keeps one acquisition's resident set flat rather than proportional to its size. No structures scale with `branches × files`.
- **Statelessness** — Latest entries and lock state live together in the store the lock contract describes. A durable store keeps both across a server restart. The server's in-memory `local` store (`lore-server/src/lock/store.rs`) doesn't, and either enforcement axis can be strict on it: a restart clears every held lock and every latest entry. Held sessions end without concluding, so their published but unconcluded edits become their holders' risk. The backfill-completion marker goes with the entries, so the repository returns to its state before backfill until an operator runs a fresh survey and backfill again: chain writes stop, every acquisition is a first edit, and both enforcement axes act as advisory whatever their keys say. A restart suspends causal protection, and it can drop protection for a concluded edit that hasn't been merged everywhere, because the re-run backfill seeds from the survey's nomination, which can predate that edit. Persisting the `local` store closes that case, and is later work. A server configured with no lock store (mode `none`, in `lore-server/src/server.rs`) has no causal locks and no chain, and the enforcement keys have no effect. Scope entities live in the mutable store. A server holds in process each repository's enforcement policy, its backfill marker, and whatever it caches of its definition of unmergeable files, which a change reaches within the configured bound [Enforcement policy](#enforcement-policy-goal-9) states — a server that hasn't yet seen a completed backfill skips a conclusion, as one that lands while backfill runs is skipped — and each branch's scope, which never changes after creation and so never goes stale. Clients hold no state beyond lease renewals they haven't sent yet, which they replay after reconnecting.
- **Availability** — Every push that changes an unmergeable file now depends on the lock store, which no push touches today. While the store can't be reached, acquisitions, releases, and renewals fail with a retryable `UNAVAILABLE`; a push that changes no unmergeable file lands, and any conclusion it would make waits for a retried push or `lore lock release --conclude`, as after a fault between the branch advance and the chain write; and a push that changes an unmergeable file follows its policy — refused with a retryable `UNAVAILABLE` under lock-strict, because strict means the server never lands a change it can't check, and landed with a warning and an audit record under lock-advisory or before backfill completes. A transient read error during the walk fails the request the same way rather than taking the stricter fallback. An outage therefore blocks pushes of unmergeable files in strict repositories and nothing else, and the in-memory `local` store, which runs in-process, never reaches the case.
- **Determinism** — Chain advance is a deterministic function of the conclusions the server sees and the lock state each meets. The same sequence of acquisitions, pushes, and releases yields the same sequence of chain latests. The lock check is a function of four inputs: the stored chain latest, F's content history on the branch, the hop budget, and whether each revision the walk reaches can be read. A walk that exhausts the budget gives the indeterminate result rather than ahead or behind, so a different budget can give a different answer for a branch many edits ahead. A revision on the walk that can't be read, because it was obliterated or pruned, sends the walk looking for the chain latest's revision itself for the rest of its length, which misses a branch that reached the same content by another route. Obliteration and pruning are permanent, so an unreadable revision stays unreadable, and the same inputs give the same answer on every request. A transient read error isn't an input: it fails the request as retryable rather than taking that fallback.
- **Observability** — The proposal introduces new server-side state (latest entries, lock entries, scope entries) and new failure modes (causality denial, indeterminate denial, lock contention, lease eviction) that operators need to monitor and debug. The design phase specifies a metrics surface covering at minimum: lock-acquisition success rate and denial rate broken down by reason (chain-behind, indeterminate, contention, not-found-in-branch), with the overrides granted past indeterminate; chain-advance rate per scope; pushes refused for holding no lock, and off-protocol edits; lease renewals, lease-eviction events, and releases that left published edits unconcluded; locks moved between branches; quiescent-latest collapse events (if the optimization is enabled); scope lifecycle events (create, rename, archive, restore, purge); and lock-store operation latencies. An append-only audit trail for chain advances — recording `(revision, scope_id, file_id, branch_id, holder_user, timestamp)` for each advance, and every off-protocol edit — is the operational counterpart to the durability of the latest entries themselves; without it, "who advanced this chain" turns into archeology against revision metadata.

Telemetry lands with the phase that produces its signal: scope lifecycle events with phase 1; abandoned reservations, lease expiries, and the live-entry count with phase 3; acquisition outcomes, moves and force-releases with their audit records, and what advisory policy accepted with phase 4; bridge translation, unresolvable locks, and migration reports with phase 5; chain advances, conclusions a retried push completed, off-protocol edits, hold durations, and the chain-advance audit trail with phase 6.

**Nothing changes behavior on deploy, except phase 6.** Each phase reaches a live fleet as a rolling deploy, so two server versions run concurrently against the same state for its duration. A phase whose behavior changes when its binary lands behaves two ways at once — and for the phase that redirects the existing lock service onto the new state, that means one server granting a lock the other can't see, silently. So code ships inert behind a flag, the fleet reaches one version, and a fleet-wide configuration flip enables the behavior. Rollback is the reverse flip rather than a redeploy, which is what makes it fast enough to use.

Phase 6 takes no flag: its deploy turns enforcement on, and the repository's keys decide what it does. Until the deploy finishes, a push to the holder branch concludes on a server carrying the phase and keeps the lock on one that doesn't; a push an older server lands unchecked can be refused by a newer one, under a strict key or the user check; and a repository created during the deploy, which gets the backfill marker at creation and reads an absent key as strict, is strict on the newer servers at once. Each outcome is one the protocol allows on its own — a kept lock concludes at the holder's next push or with a concluding release, and a refused push is one the whole fleet refuses once the deploy finishes — so none loses work or grants a lock twice, the failures the flags of phases 4 and 5 guard against. Setting both keys to advisory on every existing repository before the deploy keeps refusals from depending on the server.

**Storage and policy first, enforcement last.** Scope entities, the definition of unmergeable files, and the lock store all land and sit unused. The new lock service goes live next, still advisory on both axes, so the checks run and report while nothing is refused — which is what tells an operator the denial rate they'd be signing up for, and which tools still edit unmergeable files without locking. The server then redirects the existing lock service onto the same state, so both surfaces see one set of locks. Before it does, it counts the existing locks that wouldn't resolve to a file — on files not yet pushed, or on resources that aren't files — so their users are known before those locks start being refused. Only then does enforcement come on, per repository, and only once the repository's survey and backfill have run.

**Backfill runs before either axis goes strict, and chain writes start when it completes.** A repository writes no latest entry until its backfill has completed, and both enforcement axes act as advisory until then, whatever their keys say. The chain axis has nothing to judge against before then. The lock axis depends on the entries as well, because adoption is defined against them: with no entries no push can be adoption, so a strict lock axis would refuse every catch-up merge for contention while any branch held the file. Before completion, locks give exclusivity, a conclusion releases without writing the chain, and every acquisition is a first edit — today's protection. Gating strict policy alone wouldn't be enough: under advisory policy an acquisition with no entry is still a first edit, and if its conclusion wrote the chain, whichever branch locked first would seed it, and backfill, which writes only where no entry exists, would keep that seed. A conclusion that lands while backfill runs is skipped. That leaves an entry older than the concluding branch, which the ahead rule grants, but it grants every branch still at the older content too, so that concluded edit has no protection until the scope's branches have merged it. Backfill records its completion in the lock store next to the latest entries, so a store that loses the entries loses the marker with them, and re-running backfill after a restart of the in-memory store is an operator step that starts with a fresh survey. A repository created after the code is deployed has nothing to backfill, so it gets the marker at creation. A file that becomes unmergeable later gets a backfill of its own, as [Unmergeability](#unmergeability) describes.

**A survey measures divergence before enforcement meets it.** Free branching without a chain has already produced unmergeable files sitting at different content across branches of what becomes one scope. Backfill can only choose one of those as the chain latest, and every branch that doesn't contain the chosen content is behind from that moment. With no entries before backfill, the survey's nomination is what backfill writes wherever branches disagree. Where one branch's content for the file has every other branch's content in its history, the survey nominates that content, since every other branch is then genuinely behind or caught up against it. Where branches diverge, it nominates the content the most branches come out caught up or ahead against, and the repository's owners accept the branches that choice leaves behind before backfill runs. Backfill seeds each entry with the nominated content and the revision that produced it, found the way a conclusion finds it. The [ahead relation](#lock-acquisition-goal-1-goal-3) narrows this — a branch that merged the winning content at some point is unaffected — but what remains is real, it's inherited rather than created by this proposal, and it's the largest adoption risk in the rollout. A read-only survey reports the exact set before backfill writes anything.

**Two things the original sketch of this plan got wrong.** It called for stamping every existing branch with a scope id in a bulk write; deriving the default scope's identifier from the repository makes that unnecessary, since an absent scope on a branch already resolves to the right answer. And it placed latest entries in the mutable store, which [Per-file chain latest](#per-file-chain-latest-goal-1-goal-2-goal-7) revises.

**Rollback.** Phases 1 through 3 roll back by reverting their code, since nothing reads the state they add, which persists harmlessly. Phase 9 reverts too, and merge loses its pre-flight. Phase 7 writes nothing. The others roll back as follows:

- **Phase 4, causal lock service.** Turning `causal_locks` off sends new clients back to the existing lock service. The new store's entries persist, unread.
- **Phase 5, bridge.** `lock_bridge` steps back one value. Before the cutover, turning it off returns the existing lock service to its old table while the new store keeps serving the new lock service. After the cutover it steps back to dual-read, never to off: every lock taken or released since lives only in the new store, and dual-read keeps those visible and contended while new locks from old clients go to the old table again, so no rollback grants a lock twice. The signal to roll back is a dual-read divergence during the window before cutover, and after it a rate of failed legacy lock calls — contention between branches that now share a scope, or locks that don't resolve to a file — above what the migration report predicted.
- **Phase 6, enforcement.** Setting both enforcement axes to advisory, per repository or across the fleet, stops every refusal the axes control, while the server keeps advancing chain latests where backfill has completed and recording what strict policy would have denied. Four refusals no policy key controls stay in force: contention between acquisitions, the push-protected permission a lock on a protected branch takes, a lock that doesn't resolve to a file, and the refusal to archive a branch that holds locks. A push to the holder branch keeps concluding by default. Locks stay per-scope, because the bridge rolls back separately. Removing the phase altogether, conclusion at push included, is a redeploy of the previous version, since no flag turned it on.
- **Phase 8, backfill.** Stopping a run before it completes writes no completion marker, so chain writes don't start and neither axis goes strict, and every entry the run wrote names a real revision, the one that produced the nominated content. After completion, setting both keys to advisory is the lever. The signal is a sustained chain-behind rate that doesn't match the branches the survey called behind, which points at a backfill or chain-state error rather than at stale work. Because the rollout completes backfill with both keys set to advisory, those results show first as warnings, before the server refuses any branch.

## Security Considerations

The new mechanism does not change Lore's trust boundary. Latest writes are server-side, gated by server-verified lock ownership; clients never directly mutate latest entries or scope state, and the generic mutable-store write path refuses the scope key types. The server decides which files a push changes by comparing the revisions' trees, never from the record of a revision's changes the client writes, which nothing on the server checks. A branch's scope is set only at branch creation, by the server: no branch-metadata write can add, change, or remove it, so no writer can move a branch out from under its scope's chain. Lock acquisition takes the permission a push to the branch it names takes, through the same check the push handler makes (`PushAccess`, in `lore-server/src/grpc/handlers/branch_push.rs`) — write access for an unprotected branch, the push-protected permission for a protected one — on both lock services. Today's `Lock` call checks write access alone (`lore-server/src/grpc/lock_service.rs`); with the push check, a caller cannot lock a file on a branch they could not push to, and the server accepts a branch a request names only when the caller can push to it. Moving a lock takes the same permission on the branch it moves to, and only the user the lock records can move it, so a move neither takes another user's lock nor carries one out of its scope. Other branches in the scope don't enter the check: requiring push access to every protected branch in the scope would stop ordinary contributors, who reach `main` through a change request, from locking anything. The server assigns every acquisition's transaction id, so a client can't pick an id that never yields. The administrative operations map onto the repository's existing roles: force-unlock, granting past an indeterminate result, changing the enforcement keys, and changing the definition of unmergeable files as repository configuration take `Owner` or `Admin`; concluding a session on another user's behalf takes `Owner`, `Admin`, or a repository permission granted for it; and scope administration takes repository administration or the scope's creator — except scope creation, which takes write access, and purge, which takes repository administration alone.

On the holder branch the lock is the user's as well as the branch's, so under strict policy nobody else who can push to the branch edits the file on someone else's lock. With authentication off, every caller is the same user, `<unknown>` (`get_user_id_from_token_ref`, in `lore-server/src/util/mod.rs`), so the user check reduces to the branch there. A server set to trust unsigned identities (`server.trust_unsigned_identity`) takes each caller's user from its unsigned token, so there the user check compares identities any caller can claim. It joins the other limits of running without authentication: the permissive authorizer grants write access and no elevated role (`AllowAllRepositoryAuthorizer`, in `lore-server/src/authnz/repository_authorizer.rs`), so force-release and granting past an indeterminate result aren't available.

A malicious caller cannot construct a chain latest that bypasses content integrity: latest entries reference revisions that themselves go through the existing content-addressed validation. Only a conclusion writes the chain, a conclusion takes the lock, which requires satisfying the causal check, and the server refuses a conclusion it proves behind. The causal check reads the file-history index each revision carries — Lore's per-file-id back-pointer, which names the earlier revision that last changed each file. The client writes that index when it commits, and nothing on the server checks it: the server hashes every payload a client pushes against its address ([ADR 00023](../developing/decisions/00023-data-verification-and-trust.md)), which proves the index arrived as the client wrote it, not that it's true. A client that forges it can therefore make a branch that's behind look ahead, take the lock, and conclude. That gains nothing a user who can push doesn't already have: merging the chain's content, taking the lock, and pushing older content is an ordinary edit. The protocol keeps users from building on stale content by accident. It doesn't stop a lock holder from deliberately writing any content, and history keeps both versions either way. The push gate itself doesn't depend on that index, because the tree comparison decides which files a push changes. A client that predates this proposal goes through the same checks on the calls it already makes, so under strict policy it can't hold a lock while behind or conclude from behind. A change that makes a file mergeable or unmergeable, including a change to the definition of unmergeable files that a push carries, needs the lock while the file is unmergeable on either side, so no sequence of pushes edits an unmergeable file outside the protocol by making it mergeable first. A change to the definition made outside a push doesn't pass that check, which is why it takes `Owner` or `Admin`: making a file mergeable drops its protection. Advisory policy relaxes these checks by the repository's own choice, and records every edit it accepts.

**Locks are a denial-of-service exposure by design.** A lock covers its whole scope, so any writer can lock every unmergeable file in a scope from a branch they can push to, and refuse every other branch's edits to those files until the locks are released. That's inherent in scope-wide exclusive locks, and this proposal adds no limit. An administrator releases everything one user holds with one command, and revoking write access is the answer to a malicious user.

## Privacy Considerations

Latest entries hold `Hash(scope_id, file_id)`, the chain latest's revision, and F's content hash at it — nothing that names a user, and no path. A latest entry marked with an off-protocol edit also names the branch and time of that edit, which the revision history already records. Lock entries (per the lock contract in Proposed Design) associate `(scope_id, file_id)` with the holder's `branch_id` and user, as today's lock entries do, and existing lock queries already expose both. A lock migrated from the existing lock service records the path inside the repository that owns the file, derived from its node, because a client that predates this proposal addresses its locks by path; today's entry holds a path too, though for a file behind a link it's the mount path the caller typed. Two new records do name users. The append-only audit trail records each chain advance with the holder's branch and user, each force-release with the administrator and the prior holder's branch and user, each move with its user and both branches, and every off-protocol edit. It goes to the server's structured log stream, so it outlasts the lock it describes, and its retention and redaction follow that pipeline's policy rather than lock state's. A change to a repository's lock configuration — the enforcement keys or the definition of unmergeable files — leaves a repository audit event naming who made it. Apart from those, no new user-identifiable data is collected, persisted, or made visible beyond what existing lock state already exposes, and deletion and redaction of lock and revision data follow the existing policies.

## Risks and Assumptions

**Assumptions**

Checked against the tree, two of these don't hold, and the design changed accordingly. This section records each finding inline, with its code citation, rather than quietly deleting the assumption.

- **Assumption:** Lore's per-file-id back-pointer index (file-history blocks; `lore-revision/src/file/history.rs`; surfaced via `find_last_modified_revision` in `lore-revision/src/revision.rs`) resolves "most recent F-modifying revision in B's linear history" in roughly the same cost as a Merkle leaf traversal — and is updated atomically as part of every revision that modifies the file. *Invalidated if:* the back-pointer requires a separate index lookup with materially different cost, or if it lags revision creation in a way that exposes stale answers to the lock check. **Holds, with a caveat:** the helper is the right primitive precisely because the file-history weave lags one revision behind a branch's latest revision, so that revision's own delta has to be consulted before the back-pointer. Reading the pointer alone reports one revision too far back on a branch that just committed. The helper is private and shaped for merge, so it needs opening up rather than calling. A second caveat: a revision whose tree was built from another revision than its first parent — a merge reconciling divergent history, a revision that commits a link — can give a file another node id there, and the weave records the file's history on its counterpart, matched by file id or else by path (`find_counterpart_node`, `lore-revision/src/state/counterpart.rs`). Each history entry records the file's node id in the revision it points to beside the revision itself, so a walk over that history follows the recorded id rather than the same node id, a step that costs what any other does. At a merge it follows the merge slot's revision and id as well, so a file a branch holds only through a merge's other parent is found, and a line of that history ends where an entry records the file added without a merge, as the merge path's own history walk does (`find_last_merged_revision`, `lore-revision/src/revision.rs`), or where the node it names holds another file.
- **Assumption:** Lore's per-file-id back-pointer can be queried specifically for *content-changing* revisions (revisions where the file's BLAKE3 content hash changed), distinct from tree-entry changes that only updated metadata or path-of-record. *Invalidated if:* the back-pointer cannot distinguish content updates from metadata- or rename-only changes — in that case the protocol must filter at lookup time (skipping back-pointer hits whose tree entries match the previous content hash) or treat the divergence as a fallback path. **Invalidated:** the commit path advances the pointer for every entry in a revision's delta whatever its action (`record_first_parent_change`, in `lore-revision/src/commit.rs`), so a rename advances it exactly as a content edit does. The proposal takes the filtering fallback it anticipated, which is why the caught-up check compares content and keeps revision identity as the secondary form.
- **Assumption:** `file_id` is stable across rename, move, and content edit, and is unique per file across the repository. *Invalidated if:* a rename or move produces a new `file_id`, or `file_id` is recycled after deletion, in which case identity has to be re-keyed. **Holds:** `file_id` is the address's context, seeded with a UUIDv7 when the file is added (`lore/src/revision_tree/add.rs`); a move keeps it, a modify keeps it unless the caller supplies a replacement, and a staged delete followed by a re-add restores it.
- **Assumption:** Per-file, per-scope lock-acquisition rate is bounded by human or coordinated automation rates (≤ a handful per second per file per scope). *Invalidated if:* an uncoordinated automated workload attempts thousands of lock cycles per second on one (scope, file) pair, making the single-key write a hot spot in the lock store. **Holds:** nothing in this proposal raises the rate, and the derived key spreads files evenly across the store, so contention stays confined to the one file.
- **Assumption:** Lore already has a distributed-commit mechanism that can advance multiple branch-latest-like rows atomically. *Invalidated if:* multi-file unmergeable pushes have to invent a new atomicity protocol. **Invalidated:** branch advance is a single-key compare-and-swap (`try_store_latest`, in `lore-server/src/grpc/handlers/branch_push.rs`) and the mutable store offers no transaction (`MutableStore`, in `lore-storage/src/mutable_store.rs`). Rather than inventing one, the design orders the writes so every intermediate state is safe: the branch advances first, and each file's chain write and release follow. A fault between them leaves the lock held and the chain at the previous session, and the pusher's retry or the holder's concluding release completes the conclusion. Cross-key atomicity turns out not to be needed; what relying on the retry costs is under Risks.
- **Assumption:** The number of scopes per repository stays modest (single digits to low tens). *Invalidated if:* workflows demand hundreds or thousands of scopes per repo, in which case per-scope entry count and scope-lookup caching strategies need re-examination. **Doesn't need to hold:** nothing on a request path scales with the scope count — a branch belongs to one scope, and lookup is one cached read — so the design sets no limit. Storage doesn't multiply either, since a scope holds an entry only for a file concluded in it or seeded there by backfill, which is what makes a short-lived isolation scope cheap enough to reach for freely.

**Risks**

- **Risk:** Archiving a branch that still holds locks leaves those locks held for a branch nobody works on, refusing every other branch in the scope until they expire. *Mitigation:* `lore branch archive` is refused while the branch holds locks, until the holder releases or concludes them or an administrator force-releases them, which is one query of the held locks. Archiving a branch whose revisions a chain latest names needs no precondition: an archived branch keeps its id, history, and latest revision, so a branch behind it catches up by merging it by id, and the denial says how.
- **Risk:** A scope `purge` while branches still reference the scope_id would leave those branches naming a scope that doesn't exist. *Mitigation:* `lore scope purge` is refused while any live branch names the scope; an archived branch that names it can't be restored afterward, and its work stays reachable by merging it by id. Ordinary `lore scope archive` is a soft operation that drops only the name → id mapping, so chain state and branch references stay intact and the action is reversible via `lore scope restore`.
- **Risk:** Users misplace work in the wrong scope (branch off main when they meant to branch off a release scope, or vice versa) and discover it only when a lock denial points at an unexpected scope. *Mitigation:* `lore branch info` surfaces scope membership prominently; `lore branch create` confirms the inherited scope; lock-denial errors name the actual scope so the mismatch is legible.
- **Risk:** Long-held locks on hot unmergeable files become a productivity bottleneck within a scope. *Mitigation:* a push to the holder branch concludes by default, so a lock lasts until its holder's next push of the file unless the holder keeps it; the lease, which the holder's own work renews and which reaps only idle sessions; the admin force-release path; and the short-lived isolation scope for work that can't wait. Across scopes the risk does not amplify — independent scopes do not contend.
- **Risk:** Concluding at push advances the chain to work on a feature branch before that work lands, so a feature branch abandoned after concluding leaves the scope's other branches behind until they merge it or adopt its content. *Accepted:* a session that ends at the push publishing its edit keeps locks short, and the alternative, [concluding only when the work lands](#conclude-only-when-the-work-lands), blocks every other branch in the scope from the file for the life of a feature branch. Tooling that wants the chain to follow only landed work keeps the lock (`lore push --keep-lock`) and concludes when the work lands (`lore lock release --conclude`).
- **Risk:** A holder releases, moves the lock to another branch, or the lease expires, while published edits to the file sit unconcluded on their branch, and another branch concludes over them. *Mitigation:* a push to the holder branch concludes by default, so unconcluded published edits exist only while a holder keeps the lock; the lease renews from the holder's work on the file, so expiry reaps only idle sessions; `lore lock release` warns when the branch holds unconcluded published edits and points at concluding instead, and a move warns when it leaves such edits behind; and overtaken edits are never lost silently — landing them later is refused under strict policy or recorded as off-protocol under advisory.
- **Risk:** A server fault in the window between a concluding push's branch advance and its chain writes leaves the session unconcluded until the client retries or the holder concludes with `lore lock release --conclude`. With neither, the lease reaper releases the lock without concluding: the merged work loses protection, and other branches stay refused for contention until then. *Accepted:* relying on the client's retry, which the CLI makes on a transport failure, is a deliberate trade for cost and simplicity rather than an oversight. Making the server complete the conclusion on its own would mean recording the pending conclusion on each lock entry before the branch advances, at a write and a store round trip per concluded file on every concluding push, plus the recovery paths that read it back. That's worth paying only on a durable lock store, and an implementation can adopt it if the reliance on retries proves insufficient.
- **Risk:** A lock-store outage blocks every push that changes an unmergeable file in a repository whose lock axis is strict. *Mitigation:* the refusal is a retryable `UNAVAILABLE`, which the client retries; pushes that change no unmergeable file keep landing; and the policy keys live in repository metadata rather than in the lock store, so an `Owner` or `Admin` can set the lock axis to advisory for the outage's length, as a recorded audit event, which reaches every server within the policy's propagation bound.
- **Risk:** During phase 6's rolling deploy the same push is treated two ways, depending on which server takes it: concluded on a server carrying the phase and kept on one that doesn't, and, on a repository whose keys read strict, refused on one and landed unchecked on the other. *Mitigation:* every outcome is one the protocol allows on its own, so none loses work or grants a lock twice; setting both keys to advisory on every existing repository before the deploy keeps refusals from varying, and a lock kept by an older server concludes at the holder's next push.
- **Risk:** A restart of a server running the in-memory `local` lock store suspends causal protection: sessions end without concluding, chain writes stop, and both axes act as advisory until an operator re-runs the survey and backfill. The re-run can also drop protection for a concluded edit that hasn't been merged everywhere, since the survey's nomination can predate it. *Accepted:* a durable store avoids both, and making the `local` store durable is later work that closes the restart case.
- **Risk:** Backfill races with concurrent edits, producing stale or wrong latest entries. *Mitigation:* no conclusion writes the chain until backfill completes, so nothing competes with it. What remains is accepted: a conclusion that lands while backfill runs is skipped, which leaves an entry older than the concluding branch, and the ahead rule grants that branch and every branch still at the older content, so that concluded edit has no protection until the scope's branches have merged it.
- **Risk:** A branch created with an explicit scope against a server that predates scopes silently lands in the default scope, where it stays. *Accepted:* scopes need an updated server, the release notes say so, and branch info after the first push shows the scope the server assigned.
- **Risk:** Repository policy drifts toward advisory enforcement habitually, defeating the protocol's safety guarantees through configuration rather than through code. *Mitigation:* a metric counts what advisory policy accepted, by the outcome strict policy would have produced, and the audit trail records each such event, making the cost of the policy choice visible; relaxing either axis takes a repository `Owner` or `Admin` and leaves a repository audit event, so a relaxation is an explicit, attributable act rather than a default.

## Drawbacks

- Every unmergeable file concluded in a scope, or seeded there by backfill, gains always-on server-side state there that did not previously exist, even one rarely edited again; storage and operational tooling have to cover it indefinitely.
- Adds a new lock failure mode (causality denial) distinct from contention denial; users need to learn the difference between "someone else holds the lock" and "you're behind on this file in this scope."
- Scope is a new concept users have to model whenever they go beyond the default — scope creation, branch assignment, and cross-scope merges all become explicit decisions.
- Downstream tooling that wants to rely on strict chain semantics — for example, CI checks that assume the chain latest is authoritative — must either depend on the per-repository strictness policy or treat the chain as best-effort, complicating any integration that prefers not to be policy-aware.
- Locks on mergeable files become per-scope for existing users, so two branches in one scope that each held a lock on the same path contend for it.

## Alternatives Considered

### Per-branch ephemeral locks (status quo)

Keep existing exclusive locks, scoped per branch or globally, without a causality check. Trust users to merge before locking.

*Rejected because:* this is exactly the model Motivation argues is structurally incomplete. The harm of a missed merge is not visible until merge time, and the cost at that point — discarded work on an unmergeable file — is precisely what the lock was supposed to prevent.

### Auto-merge on lock denial

When the lock check fails, the server merges the chain latest's revision into the requester's branch automatically before granting the lock.

*Rejected because:* merging a revision brings in not just the F edit but the source branch's entire causal closure up to that point, including changes unrelated to F. The user must decide whether and how to accept those changes; this proposal makes the decision explicit by surfacing the denial instead of silently doing a non-trivial merge on behalf of the lock requester.

### Single-trunk model for unmergeable files

Disallow editing unmergeable files outside a designated trunk (such as `main`). All edits must happen on trunk.

*Rejected because:* it forces every artist or pipeline that touches an unmergeable file onto a single branch, eliminating the value of Lore's free branching for the workflows that most need it (long-running feature branches, parallel content streams, experimental work).

### Single global chain per file (no scopes)

Keep one chain per file across the entire repository. Lock check is always against the global chain latest; release branches, experimentation, and main all share one chain.

*Rejected because:* a single global chain over-couples independent lines of work — a backport on a release branch blocks every editor on main, an experimental edit on a sandbox branch freezes the same asset for everyone else. The proposed design retains this model as the degenerate case (a repository that only uses the default scope operates exactly this way) while users create more scopes when their workflow needs them.

### Scope tied to specific branches (scope-as-branch-attribute)

Tie scope identity to a designated "scope branch" — the branch's identity *is* the scope. Membership is derived from descent: any branch derived from a scope branch joins its scope. No separate scope entity exists.

*Rejected because:* scope lifecycle becomes coupled to one specific branch's lifecycle. Archiving the anchor branch needs ad-hoc machinery to preserve or transfer scope identity; renaming a scope branch either loses chain history (if scope id was the branch name) or requires a separate stable id alongside the branch — at which point a decoupled scope entity is already implicit. Treating scope as a first-class entity removes these awkward dependencies: branches come and go, scopes persist as long as their chain state and branch references do.

### Materialized (branch × file) up-to-date matrix

Precompute, for every (branch, unmergeable file) pair, whether the branch is at the chain latest. Lock check is a single keyed read.

*Rejected because:* at 10K branches and tens of millions of files, the matrix has at least 10⁴ × 10⁷ = 10¹¹ cells, and sparseness doesn't bound its writes. A conclusion invalidates that file's cell on every other branch in the scope, up to 10⁴ writes for one conclusion, and a merge or push rewrites the cell of every unmergeable file it changes for every branch it affects. A content comparison, plus a walk bounded by the file's own history when the branch isn't caught up, delivers the same answer without materialization, so the matrix earns nothing.

### Bloom filters or reachability bitmaps for descendancy

Precompute revision-reachability structures to answer "does B contain the chain latest's revision?" directly.

*Rejected because:* the content check is strictly simpler and equally correct given the chain invariant — F's content history on a branch already captures its position in the chain, and the walk over it is bounded by the chain latest's revision number. Reachability bitmaps remain useful for general history queries but are not required for this one.

### CAS on the latest entry

Treat the chain latest as a contended write target, advanced by compare-and-swap at every push, as the coordination mechanism instead of the lock.

*Rejected because:* the exclusive lock already guarantees that only the holder can advance the chain latest while it is held, and it tells the editor *before* the work that nobody else is editing the file, which a compare-and-swap at push can only report after the work exists. The one conditional chain write that remains is backfill's, which writes only where no entry exists yet.

### Conclude only when the work lands

Keep each lock until its work merges to the scope's final branch, so a push to the holder branch releases nothing by default and the chain advances only to landed work.

*Rejected because:* the protocol tracks causality by content, so a session doesn't need to outlive the push that publishes its edit. A branch that later takes that content in is caught up or ahead whichever revision concluded it, so waiting for the merge protects nothing a push-time conclusion doesn't. What waiting costs is exclusivity: a lock held for the life of a feature branch blocks every other branch in the scope from editing that file for as long as the feature takes, which makes the long-held-lock risk under [Risks and Assumptions](#risks-and-assumptions) the default rather than the exception. Tooling that wants this behavior still gets it, by pushing with `lore push --keep-lock` and concluding at landing with `lore lock release --conclude`.

### Moving a lock by releasing and reacquiring

Leave the lock contract without a move, and have a user or tool that moves work between branches release each lock on the old branch and acquire it on the new one.

*Rejected because:* another branch in the scope can take the lock between the release and the acquisition, and for a set of files that gap spans the whole set, so moving a large change races every other acquirer in the scope. A move leaves no gap, because the source branch holds each lock until the move confirms, and it runs every check the acquisition would have run.

### Moving locks with the branch commands

Have `lore branch create` and `lore branch switch` move the locks of the files whose edits they carry, without being asked.

*Rejected because:* a move decides what the source branch can push next, and a branch created for unrelated work while edits sit in the working tree would take that branch's locks with it. `switch` can also reach a branch that's behind, which would leave a branch command half done on a refused lock. The commands name the locked files instead and point at `lore lock acquire --from`, and an automatic move can be added later without changing what an explicit one does.

## Prior Art

- **[Perforce](https://www.perforce.com/manuals/p4guide/Content/P4Guide/resolve.lock.exclusive.html).** Exclusive locking comes in two flavors: the `+l` filetype modifier (prevents others from opening for edit) and the `p4 lock` command (prevents others from submitting). Both are *per-branch / per-stream*: the same logical file in two different streams can be independently locked, edited, and submitted, and the divergence surfaces only at integration. Under Perforce's stream model (mainline, release, development, task, virtual stream types with parent-child hierarchy and copy-down / merge-up flow), this is structurally the same gap this LEP closes — Perforce shops that need cross-stream lock causality build custom server-side triggers that walk the stream hierarchy ([discussed at length on the perforce-user list](https://perforce-user.perforce.narkive.com/s3Mqig5m/p4-exclusive-checkout-across-branches)). Perforce's personal servers, its distributed workflow, take a [global exclusive lock](https://help.perforce.com/helix-core/server-apps/dvcs/current/Content/DVCS/fetching.exclusive.html) on a `+l` file in the shared server when a user runs `p4 edit --remote=remote`, held until the user pushes the file or reverts it with `p4 revert --remote=remote` — a partial answer scoped to personal-server topologies rather than general stream-graph causality. The lesson: as soon as branching enters the picture, lock primitives need branching-graph awareness to be sound; Perforce demonstrates this by negative example, lacking that awareness in the core protocol.
- **[Git LFS file locking](https://github.com/git-lfs/git-lfs/wiki/File-Locking).** Provides server-side locks for LFS-tracked files, held until released or pushed. Locks are **repository-wide and keyed by file path**, the opposite of Perforce's per-branch scoping: a lock taken in one branch prevents *other* users from editing that path on any branch ([explainer](https://www.vikram.codes/blog/2024/3/22/git-lfs-file-locking)). This avoids the divergent-edits-across-branches failure mode that Perforce streams have, but introduces three weaknesses this LEP avoids by construction:
  - **Path-keyed identity:** because Git LFS keys the lock by file path, renaming a locked file loses the lock — "when you rename an exclusively-locked file, the lock is lost. You'll have to lock it again to keep it locked." This LEP keys on `file_id`, which is stable across renames.
  - **No causality at acquisition:** the cross-branch lock blocks *other users* on other branches, but does not check whether the *requesting branch* has observed the most recent committed edit before granting. A stale branch can acquire and edit, and the divergence is detected at push or merge rather than at lock acquisition. This LEP makes the causality check primary.
  - **Cross-branch overreach with no scoping primitive:** because every lock is repository-wide, a release-branch hotfix on a binary asset blocks every other branch from editing that asset until it's released or merged — the [exact merge-friction problem](https://gitlab.com/gitlab-org/gitlab/-/issues/224462) Git LFS users report. GitLab's [two kinds of file lock](https://docs.gitlab.com/user/project/file_lock/) — exclusive Git LFS locks that hold on every branch, and locks set in its UI that hold on the default branch only — are a workaround; this LEP solves it with first-class scopes that branches join independent of the branch graph. The lesson: a *repository-wide path-keyed lock* over-blocks; a *per-branch lock* under-blocks; this LEP's *per-scope file_id-keyed chain* is the construction that does neither. Also worth flagging as a cautionary tale: [the GitHub web UI bypasses LFS locks entirely](https://dev.to/devactivity/unlocking-productivity-why-githubs-web-ui-must-respect-git-lfs-locks-2afb) — an enforcement gap that demonstrates the importance of routing every mutation path through the lock check rather than trusting clients to consult it.
- **[Plastic SCM / Unity Version Control smart locks](https://docs.unity.com/en-us/unity-version-control/smart-locks).** Server-side cross-branch awareness for locks, denying a lock when a newer version exists elsewhere. The closest known analog to this proposal; informed by the same game-asset workflows. Its **multiple destination branches** capability is the closest existing precedent for the scope concept here: each destination branch is an independent lock scope, locks on the same file may be held simultaneously across destinations without conflict, and check-ins on non-destination branches produce a `Retained` state requiring merge-to-destination — a different take on the cross-scope merge problem this LEP resolves with chain-advancing merges into the target scope. This proposal considers its design superior because it decouples causality scoping from branch hierarchies: the user acquiring a lock does not need to name or know about a destination branch — the requesting branch's own scope membership (set once at branch creation) determines the scope, so lock-time UX needs only "lock this file," not "lock this file targeting that destination." The branch graph and the scopes of lock causality are independent dimensions, where Plastic conflates them.
- **[Subversion's `svn:needs-lock`](https://svnbook.red-bean.com/en/1.7/svn.advanced.locking.html).** A file carrying the property is read-only on disk until its user takes the lock, and read-only again once the lock goes, so an editor that refuses to save a read-only file reminds the user to lock first. The Subversion book calls the property a communication tool that works independently from the locking system: any file can be locked without it, and its presence doesn't make the repository require a lock when committing. The lesson: a reminder to lock before editing helps, but without a check at the server the protection rests on habit, which is the gap this proposal's lock enforcement closes.

## Unresolved Questions

All nine questions this proposal left open have answers. They stay listed as the record of what was open at approval, each with the answer it reached and the reasoning behind it.

| Question | Settled as |
| --- | --- |
| **Multi-shard push atomicity mechanism.** 2PC, saga with compensation, or co-shard-by-revision forcing. | None of them — cross-key atomicity isn't needed. A concluding push advances the branch first and writes each file's chain latest and release after it, so a fault between them leaves the lock held and the chain at the previous session, which no branch can act on wrongly; the pusher's retry or the holder's concluding release completes the conclusion. Two-phase commit needs a transaction manager the mutable store doesn't have. This proposal rejects co-sharding outright: it would recreate the write hot spot the key derivation exists to avoid. |
| **Cherry-pick and revert of unmergeable-file edits.** Denied at apply time, or accepted as a chain advance requiring a lock? | Not a special case. Anything that changes an unmergeable file's content is an edit in the target scope on identical terms: it needs a lock held there, and without one the push is refused, which is the "denied" answer. So edit, merge, cherry-pick, revert, and cross-scope merge pass one gate rather than four. A revert landing on the content the chain already holds is adoption and needs nothing. |
| **`--supersede` authorization.** Who may roll a chain latest back? | Nobody needs to, so the operation doesn't exist. The case it served — archiving a branch whose revisions a chain latest names — needs no rollback: an archived branch keeps its id, history, and latest revision, so a branch behind it catches up by merging it by id, and archiving is refused instead while the branch holds locks. The operations that do exist take repository roles the server already has, never the branch: force-unlock and granting past an indeterminate result take `Owner` or `Admin`, as releasing another user's lock does today. Branch ownership is the wrong gate because force-release exists precisely when the holder is unreachable, and write access to the requesting branch is wrong because the target is another branch's session. Scope administration takes repository administration or the scope's creator, purge takes repository administration alone, and scope creation takes only write access, since a scope nobody else uses harms nobody. |
| **Branch scope reassignment.** Should a branch be movable between scopes? | Immutable in the first version, with the shape kept forward-compatible: only branch creation writes a branch's scope, so a later reassignment verb needs no format change, only its preconditions and an audit event. The interesting precondition — no chain latest in the old scope names a revision reachable only through this branch — needs a reachability query Lore doesn't have cheaply, and the demand is speculative. |
| **Cross-scope merge ergonomics.** Per-file confirmation, a summary, or silent? | A pre-flight summary and one confirmation: the merge reports which of the unmergeable files it touches would be granted, contended, or behind before it changes anything. Per-file confirmation is unusable for a backport touching hundreds of assets, and silence is wrong for the one operation that crosses a causality boundary deliberately. |
| **Scope merge / split.** Can scopes be combined or divided? | No verb, now or later. Both are already expressible through branch-level merges: folding scope A into B is merging A's branches into B's, each an edit in B, then archiving A, and splitting is creating a scope and branches in it. A scope-level merge would have to reconcile two independent chain latests of one file with no common chain, which is exactly the unresolvable conflict this proposal exists to prevent. Exposing a verb implying otherwise would be worse than not having one. |
| **Default scope semantics.** Which lifecycle verbs to expose, and is the name reserved? | None, and the name is reserved. Deriving the default scope's identifier from the repository makes the rest fall out: no creation write, no migration, no lookup, and nothing stored to rename. It can't be renamed, archived, or purged, because every branch with no recorded scope resolves to it, and reserving its name keeps a created scope from shadowing it in name lookups. |
| **Quiescent-latest collapse trigger.** Sweep, event-driven, or lazy? | Not built in the first version. Its consensus check as described scales with `branches × files`, which is what Goal 3 forbids, so building it as specified would trade a storage question for a latency one. A gauge ships instead, and the trigger is lazy-at-acquire if it's ever built. |
| **Enforcement policy mechanism.** Where does the policy live? | Two repository-metadata keys, consulted on every push and acquisition, and a change reaching every server within a configured bound, 30 seconds by default. Not per-scope, because a scope is a unit of causality rather than a security boundary and varying strictness within a repository would make a file's protection depend on which branch a user started from. Not server-level, because one operator switch silently relaxing every repository is the policy-drift risk in its worst form. |

Working out the design raised questions this proposal didn't anticipate, and the sections above settle them. Locks belong to the repository that owns a file rather than the one a caller reached it through, because only then does every mount of a linked repository derive the same key. A push holding no lock never moves the chain, even one that doesn't diverge from it: an unlocked chain write could race another unlocked push, or move the chain under a session another branch holds. And both enforcement axes apply to every client, because each check sits on a call that a client predating this proposal already makes.

One answer changes the text this proposal was accepted with, rather than settling a question it left open: a branch **ahead** of the chain latest is granted a lock. The accepted text contradicted itself here. Its Goal 1 required only that the branch contain every prior edit, while its acquisition check required the branch's most recent change to the file to match the chain latest, which denies a branch that took the chain latest in and edited further. Such a branch meets Goal 1's requirement — it contains every concluded edit — so this proposal grants it, as [Lock acquisition](#lock-acquisition-goal-1-goal-3) describes: denying it protects nothing and blocks work that sits ahead of the protocol rather than behind it. Force-unlock releasing a lock rather than undoing the session follows from the same rule. Release on push, by contrast, stays as the accepted text has it: a push to the holder branch concludes the session unless the holder keeps the lock.
