# Rust SDK for the Lore C library

## Summary

Add an official Rust SDK that loads Lore's published C library and exposes it as a Rust crate. Lore itself is already a Rust program, and the `lore` crate in this repository is not published. JavaScript, Python, C#, and Go each have a separate SDK that binds the C library. Rust programs outside this workspace have no equivalent.

## Motivation

The `lore` package sets `publish = false`, so another crate cannot depend on it from crates.io. Its library target is the implementation of Lore, and `lore-capi` builds that implementation into `liblore.so`, `liblore.dylib`, or `lore.dll` plus `lore.h`. [`lore-capi` is also `publish = false`](https://github.com/EpicGames/lore/blob/main/lore-capi/Cargo.toml). The header is the external contract: each operation takes global arguments, operation arguments, and a callback, and the library copies those arguments before the call returns ([`lore-capi/lore.h`](https://github.com/EpicGames/lore/blob/main/lore-capi/lore.h)).

Epic publishes that contract for other languages as separate repositories: [lore-js](https://github.com/EpicGames/lore-js), [lore-python](https://github.com/EpicGames/lore-python), [lore-dotnet](https://github.com/EpicGames/lore-dotnet), and [lore-go](https://github.com/EpicGames/lore-go). The Go SDK states that it binds `liblore.so`, `liblore.dylib`, and `lore.dll`. There is no `EpicGames/lore-rs`. A Rust program that is not part of this workspace has to bind the header itself, shell out to the `lore` binary, or build this repository and depend on unpublished path crates.

[CONTRIBUTING.md](https://github.com/EpicGames/lore/blob/main/CONTRIBUTING.md) lists language bindings with the public APIs that require a Lore Enhancement Proposal before implementation. This document is that proposal.

## Goals / Non-Goals

### Goals

- Give Rust programs outside this workspace a supported crate that talks to Lore through the published C library.
- Pin that crate to one `LORE_INTERFACE_VERSION` and refuse a library that reports a different version. The header in this tree currently defines that macro as `0.10.2-nightly` ([`lore-capi/lore.h`](https://github.com/EpicGames/lore/blob/main/lore-capi/lore.h)).
- Use Rust types, ownership, and `Result` for the operations the header already documents, starting with the local repository workflow.
- Ship the SDK as its own repository, in the same way as [lore-go](https://github.com/EpicGames/lore-go), and leave the native library as a runtime dependency rather than a crate dependency.

### Non-Goals

- Publishing the in-tree `lore` crate or any other workspace crate.
- Changing `lore.h`, the wire protocol, the on-disk format, or the existing language SDKs.
- Reimplementing Lore in a second Rust codebase.
- Wrapping the `lore` command-line interface.
- Covering every C entry point in the first release. Remotes, authentication, merges, locks, and notification subscriptions can follow once the binding approach is accepted.

## Proposed Design

The SDK is a new repository, proposed name `lore-rs`, crate name `lore-sdk` so it does not collide with the unpublished `lore` package. It dynamic-loads the C library for the host platform and resolves the `lore_*_async` entry points for the operations it wraps.

A call fills the header's argument structs, invokes the async function, and blocks the calling thread until the callback receives the end event. The header says the library copies argument bytes before the call returns, and that a string delivered to the callback is valid only for that callback. The SDK copies any string it keeps and returns a Rust value after the call finishes. `lore_shutdown` is documented as a one-time call made when no further calls will be made, so the SDK treats shutdown as terminal for the process.

The first operations are the ones a local workflow needs: create a repository, discover a checkout, status, stage, unstage, commit, history, diff, branch list, branch create, branch switch, and read or write a committed file. Each of those functions already exists on the C API. The Rust signatures take owned or borrowed Rust values and return `Result`. They do not expose the C structs.

The crate records the interface version it was built against. On load it reads `lore_version` and rejects anything that is not that version. A later Lore release that changes the header gets a new SDK release rather than a silent layout mismatch.

The native library is not linked into the crate. The caller points the process at a Lore release artifact, as the Go SDK does with its library path. The SDK does not set `LORE_USE_SERVICE` itself. When that variable is unset, Lore's own default applies.

A community prototype of this shape is at [swap/lore-rs](https://github.com/swap/lore-rs). It loads the v0.10.1 release library and exercises a local repository in temporary directories. This proposal does not ask Epic to adopt that repository unchanged. It asks Epic to decide that an official Rust binding should exist, and to host it the way the other SDKs are hosted.

## Compatibility

- **Wire format** — N/A. The SDK calls the existing library. It does not define messages.
- **Client/server protocols** — N/A. No new RPC, authentication flow, or request shape. Any remote call the SDK grows later is a call that `lore.h` already has.
- **On-disk format** — N/A. Repository bytes are read and written by the C library.
- **CLI and public API** — The `lore` CLI, `lore-capi`, and the JavaScript, Python, C#, and Go SDKs stay as they are. The new surface is a Rust crate. Existing scripts and integrations do not change. The crate's own break happens when `LORE_INTERFACE_VERSION` changes and the SDK release that understood the old header no longer loads the new library.

## Non-Functional Considerations

- **Concurrency** — The header's callback runs during the operation. The SDK does not call back into Lore from that callback. Overlapping calls from Rust threads are the same process sharing one loaded library, which is how the C API already behaves. The SDK documents that sharing instead of inventing a second runtime.
- **Memory** — Argument structs are fixed size. Strings copied out of a callback are bounded by a documented limit; a longer string fails the call. Materializing a committed file uses the header's output path so the SDK does not have to hold the whole file. A helper that returns `Vec<u8>` copies only up to a caller-supplied limit.
- **Statelessness** — `lore_shutdown` is process-wide and final. The loaded library is process state. Dropping a Rust handle does not call shutdown, because the header says to call it once when the process is finished with Lore.
- **Determinism** — The SDK adds no history of its own. Commit, tree, and file bytes come from the library.

## Migration Plan

N/A — no breaking changes, no migration required. Nothing in an existing Lore repository, client, or server changes. Adopting the crate is a new dependency for programs that choose it.

## Security Considerations

This proposal does not change Lore's trust model. The SDK loads a native library the user supplied, which is the same trust decision as running `lore` or linking `lore-go`. A substituted library can do anything that library can do. The SDK does not download that file on its own in the first version, does not disable certificate checks, and does not write credential fields into errors. Token fields stay empty unless a later, explicit authentication API sets them. Shutdown and failed loads return the library's status without adding new privileges.

## Privacy Considerations

The SDK does not add telemetry, a network service, or a new place where repository data is stored. Error text can include a path or a message the C library returned, and that text stays in the calling process. It does not change deletion or redaction inside a Lore repository, because the library still performs those operations.

## Risks and Assumptions

**Assumptions**

- **Assumption:** Rust programs outside this workspace are a real audience for Lore. *invalidated if:* Epic intends every Rust caller to live inside this repository and use the workspace crates directly.
- **Assumption:** `lore.h` remains the stable external surface that the other language SDKs bind. *invalidated if:* Epic publishes the `lore` crate, or replaces the C ABI, before a Rust SDK exists.

**Risks**

- **Risk:** A hand-maintained layout drifts from `lore.h` after a release. *mitigation:* the crate refuses a different `LORE_INTERFACE_VERSION`, and tests load a released library rather than a stub.
- **Risk:** The community prototype and an official crate diverge. *mitigation:* acceptance of this LEP decides the official home. The prototype is evidence, not the release artifact.

## Drawbacks

- Every `LORE_INTERFACE_VERSION` change requires a matching SDK release, because the Rust crate copies C layouts instead of generating them in this first design.
- `lore_shutdown` makes the binding a process-wide resource, which is a poor fit for tests that want to unload the library.

## Alternatives Considered

### Publish the in-tree `lore` crate

Remove `publish = false` from [`lore/Cargo.toml`](https://github.com/EpicGames/lore/blob/main/lore/Cargo.toml) and tell Rust callers to depend on `lore`.

*Rejected because:* that crate is the system, not a binding. It pulls the workspace implementation into every caller, and `lore-capi` exists specifically so other languages do not do that. The other official SDKs bind the C library from their own repositories.

### Call the C header directly from each Rust program

Leave `lore.h` as the only Rust-adjacent interface and publish no crate.

*Rejected because:* the header's contract is real, and the callback, string, and shutdown rules are easy to get wrong in each caller. The Go, C#, Python, and JavaScript repositories exist to hold that binding once. Rust is the one language those repositories skip, even though Lore's own implementation is Rust.

### Shell out to the `lore` binary

Parse CLI stdout from a subprocess.

*Rejected because:* the C API returns structured events and a completion status. Text parsing drops both, and a future CLI wording change becomes an SDK break.

## Prior Art

[lore-go](https://github.com/EpicGames/lore-go) is the closest model: a separate repository, a high-level API over the C library, and a native library supplied at runtime. [lore-js](https://github.com/EpicGames/lore-js), [lore-python](https://github.com/EpicGames/lore-python), and [lore-dotnet](https://github.com/EpicGames/lore-dotnet) follow the same split. [swap/lore-rs](https://github.com/swap/lore-rs) is an unofficial Rust prototype of that split against the v0.10.1 library. It is not an Epic project.

## Unresolved Questions

- Should the official repository be `EpicGames/lore-rs`, or is a documented community crate enough?
- The first release needs a released interface version to pin. This tree's header says `0.10.2-nightly`. The prototype pinned the v0.10.1 release. Which version should the first official crate track?
- How close to the full `lore.h` surface does the first crate need to be before it is worth publishing?
